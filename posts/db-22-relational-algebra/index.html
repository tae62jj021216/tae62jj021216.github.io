[DB] 22. 관계대수와 SQL

SQL의 밑바탕에는 릴레이션을 입력받아 릴레이션을 돌려주는 연산 체계인 관계대수가 있다. 이 글에서는 관계대수의 연산자(σ, π, ∪, ∩, −, ×, ρ, ⋈, ÷)를 SQL과 짝지어 정리하고, 가장 헷갈리는 나누기(÷)를 손으로 계산한 뒤 SQL로 검증한다.

예제는 00편의 cafedb를 쓴다. 나누기 예제에서 주문 2건(13번: 이몽룡이 콜드브루 라떼, 14번: 놀부가 콜드브루)을 추가하고 테이블을 만들므로, 아래 “실습 준비 SQL”로 cafe_practice를 만든 뒤 본문 SQL을 순서대로 실행한다. MySQL 8.4에서 실행한 결과다. ORDER BY는 보기 좋게 늘어놓으려고만 붙였다(관계대수에는 정렬이 없다).

관계대수와 관계해석

관계대수는 결과를 얻는 방법(연산 순서)을 기술하는 절차적 언어이고, 관계해석은 원하는 결과(조건)만 술어 논리(∃, ∀)로 기술하는 비절차적 언어다. 둘의 표현력은 같다. SQL은 관계해석에 가까운 선언적 언어이고, DBMS는 SQL을 관계대수 식으로 바꿔 실행한다.

기본 연산은 σ, π, ∪, −, ×(와 ρ)이고, 나머지는 기본 연산으로 만들 수 있다. 예를 들어 R ∩ S = R − (R − S), 조인은 σ(R × S)다.

주의할 점: 관계대수의 셀렉트(σ)는 SQL의 WHERE이고, SQL의 SELECT 절은 프로젝트(π)다. 이름만 보고 σ를 SELECT에 대응시키는 실수가 시험에 자주 나온다.

σ 셀렉트와 π 프로젝트

σ는 조건을 만족하는 튜플(행)만 골라 수평으로 자른다. 조건은 비교 연산자와 ∧(AND), ∨(OR), ¬(NOT)으로 적는다. 결과의 차수(열 수)는 그대로이고, 카디널리티(행 수)는 같거나 줄어든다.

π는 지정한 속성(열)만 남겨 수직으로 자른다. 관계대수는 집합을 다루므로 결과에서 중복 튜플이 사라진다. 중복을 허용하는 SQL에서는 DISTINCT가 있어야 같아진다. πgrade(member)는 SELECT DISTINCT grade FROM member이고 결과는 3행(BASIC, GOLD, VIP)이다. DISTINCT를 빼면 회원 수만큼 8행이 나온다.

연산은 안쪽부터 적용한다. “서울 회원의 이름과 등급”은 σ로 행을 고른 뒤 π로 열을 고른다.

∪ ∩ −: 집합 연산과 합병 가능 조건

두 릴레이션이 합병 가능(union-compatible)해야 쓸 수 있다. 차수가 같고, 대응하는 속성의 도메인이 같아야 한다. 2025년, 2026년 이벤트 참가자 R, S의 πmember_id, name으로 확인한다.

R = event_2025 (member_id, name)S = event_2026 (member_id, name)
101 홍길동 / 103 이몽룡 / 104 심청101 홍길동 / 105 흥부 / 107 콩쥐
  • R ∪ S = {101 홍길동, 103 이몽룡, 104 심청, 105 흥부, 107 콩쥐}. 양쪽에 있는 홍길동은 한 번만 들어간다.
  • R ∩ S = {101 홍길동}
  • R − S = {103 이몽룡, 104 심청}. 차집합은 교환법칙이 성립하지 않아서 S − R은 {105 흥부, 107 콩쥐}다.

같은 결과를 SQL의 UNION·INTERSECT·EXCEPT로 구하는 방법과, MySQL이 열 개수만 검사하고 도메인은 검사하지 않는 점 등 SQL에서의 동작은 14편에서 다뤘다.

× 카티션 곱과 ρ 개명

×는 두 릴레이션의 튜플을 모든 조합으로 이어 붙인다. 합병 가능할 필요가 없고, 결과의 차수는 두 차수의 합, 카디널리티는 두 카디널리티의 곱이다. 예를 들어 πmember_id, name(σgrade=’VIP’(member)) × πmenu_id, name(σcategory_id=7(menu))는 VIP 회원 2명과 케이크 2개의 조합이라 차수 2 + 2 = 4, 카디널리티 2 × 2 = 4다. SQL의 CROSS JOIN으로 직접 확인하는 과정은 17편에서 다뤘다.

ρ는 릴레이션이나 속성에 새 이름을 붙인다. 같은 릴레이션을 두 번 쓰는 셀프 조인에 꼭 필요하다.

πM.name, R.name(ρM(member) ⋈M.referrer_id = R.member_id ρR(member))

⋈ 조인: 세타, 동등, 자연

조인은 카티션 곱에서 조건에 맞는 튜플만 고른 것이다. R ⋈θ S = σθ(R × S). 조건에 아무 비교 연산자나 쓰면 세타 조인, =만 쓰면 동등 조인, 이름이 같은 모든 속성이 같은 튜플을 잇고 공통 속성을 한 번만 남기면 자연 조인이다(SQL에서의 구분과 NATURAL JOIN의 함정은 15편).

관계대수의 기본 조인은 짝 없는 행이 빠지는 내부 조인이고, 외부 조인은 ⟕(왼쪽), ⟖(오른쪽), ⟗(완전)로 표기한다.

÷ 나누기: “모두”를 만족하는 것 찾기

R(A, B) ÷ S(B)는 S의 B 값을 모두 가진 R의 A 값을 돌려준다. “모든 과목을 들은 학생” 같은 질의다. 결과 속성은 R에서 S의 속성을 뺀 것(A)이다.

예제: 콜드브루 메뉴를 전부 주문해 본 회원을 찾는다.

  • R = 회원별 커피 주문 내역 coffee_order(member_id, menu_id)
  • S = 콜드브루 메뉴 coldbrew(menu_id) = {4 콜드브루, 5 콜드브루 라떼}

CREATE TABLE coffee_order AS
SELECT DISTINCT o.member_id, oi.menu_id
FROM orders o
JOIN order_item oi ON oi.order_id = o.order_id
JOIN menu mn       ON mn.menu_id  = oi.menu_id
WHERE o.member_id IS NOT NULL AND mn.category_id IN (4, 5);

CREATE TABLE coldbrew AS
SELECT menu_id FROM menu WHERE category_id = 5;

R을 회원별로 모아 S = {4, 5}를 모두 포함하는지 본다.

member_idR에서 주문한 menu_id{4, 5}를 모두 포함?

R ÷ S = {103, 106}. 103은 2번도 주문했지만 S를 포함하기만 하면 된다.

기본 연산으로 풀기

R ÷ S = πA(R) − πA( (πA(R) × S) − R )

있어야 할 조합(모든 회원 × S)에서 실제 주문을 빼면 빠진 조합이 남고, 빠진 조합이 있는 회원을 전체에서 빼면 답이다. 각 단계를 CROSS JOIN, EXCEPT로도 실행해 확인했다.

  1. πA(R): 주문한 회원 = {101, 102, 103, 105, 106}
  2. πA(R) × S: 있어야 할 조합 5 × 2 = 10개
  3. ② − R: 빠진 조합 = (101, 4), (101, 5), (102, 4), (102, 5), (105, 4)
  4. πA(③): 하나라도 빠진 회원 = {101, 102, 105}
  5. ① − ④ = {103, 106}

SQL로 쓰기: NOT EXISTS 이중 부정

SQL에는 나누기 연산자가 없다. “S의 모든 메뉴를 주문했다”를 “주문하지 않은 콜드브루 메뉴가 없다“로 바꿔 NOT EXISTS를 두 번 쓴다(∀x P(x) ≡ ¬∃x ¬P(x)).

손으로 계산한 결과와 같다. S에 속한 메뉴만 남겨 회원별 COUNT(DISTINCT menu_id)가 S의 크기(2)와 같은지 보는 GROUP BY ... HAVING 방법도 같은 답을 낸다.

주의할 점: 나누기 결과의 속성은 R의 속성에서 S의 속성을 뺀 것이다. R(member_id, menu_id) ÷ S(menu_id)의 결과에는 menu_id가 없다.

SQL을 관계대수로 바꾸기

FROM → 조인·×, WHERE → σ, SELECT → π 순서로 안쪽부터 쌓는다. SELECT DISTINCT a FROM R JOIN S ON R.x = S.y WHERE c는 πa(σc(R ⋈R.x = S.y S))다. GROUP BY와 집계 함수는 기본 관계대수에 없고, 확장 관계대수에서 그룹 연산자(𝒢 또는 γ)로 표기한다.
