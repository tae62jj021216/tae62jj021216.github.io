[DB] 10. 사용자 계정과 권한

DB를 여러 사람과 프로그램이 함께 쓰면 “누가 어디에서 접속해 무엇을 할 수 있는지”를 정해야 한다. 이 글에서는 MySQL의 사용자 계정(CREATE USER)과 호스트, 권한을 주고 빼는 DCL(GRANT·REVOKE), 권한을 넘겨줄 수 있게 하는 WITH GRANT OPTION, 권한 묶음인 역할(ROLE)을 정리한다.

예제는 00편의 cafedb에서 메뉴·회원 데이터를 연습 DB cafe_practice로 복사해 쓴다(MySQL 8.4). 계정 이름은 모두 cafe_로 시작하고, 비밀번호 dummy1234는 실습용 예시값이다. 실습이 끝나면 계정을 모두 지운다.

계정은 ‘사용자’@’호스트’

MySQL 계정은 이름 하나가 아니라 사용자 이름과 접속하는 호스트의 쌍이다. 이름이 같아도 호스트가 다르면 다른 계정이고, 비밀번호와 권한도 따로 가진다.

호스트뜻
'localhost'DB 서버와 같은 컴퓨터에서 접속할 때만
'%'어느 곳에서 접속해도 (%는 LIKE처럼 “모든 문자열”)
'192.168.0.%'해당 네트워크 대역에서만
'10.0.0.5'그 IP 하나에서만

'%'는 편하지만 외부 어디서나 로그인을 시도할 수 있으므로, 필요한 곳으로 좁히는 것이 안전하다. 호스트를 생략하면(CREATE USER 'cafe_staff') '%'로 만들어진다.

USAGE는 “권한 없음”이라는 뜻이다. 계정을 만들면 로그인만 할 수 있는 USAGE가 기본으로 붙는다. 인수 없이 SHOW GRANTS;라고 쓰면 지금 접속한 계정의 권한을 본다.

주의할 점: MySQL 8.0부터는 GRANT가 계정을 대신 만들어 주지 않는다. 없는 계정에 권한을 주면 ERROR 1410 (42000): You are not allowed to create a user with GRANT가 난다. 예전 자료의 GRANT ... IDENTIFIED BY '비밀번호'도 이제는 문법 오류다. 반드시 CREATE USER를 먼저 실행한다.

FLUSH PRIVILEGES는 필요 없다

위 예제에서 GRANT 직후 새로 접속한 cafe_reader는 바로 권한을 썼다. GRANT, REVOKE, CREATE USER, DROP USER 같은 계정 관리 문은 서버의 메모리 권한 정보를 즉시 고치므로 FLUSH PRIVILEGES를 따로 실행할 필요가 없다.

FLUSH PRIVILEGES는 mysql.user 같은 권한 테이블을 INSERT/UPDATE로 직접 고쳤을 때 그 내용을 다시 읽어 들이는 명령이다. 권한 테이블을 직접 고치는 것 자체를 권장하지 않으므로, 평소에는 쓸 일이 거의 없다.

REVOKE: 권한 빼앗기

1

REVOKE 권한 목록 ON 대상 FROM '사용자'@'호스트';

1
2

REVOKE UPDATE ON cafe_practice.* FROM 'cafe_app'@'%';
SHOW GRANTS FOR 'cafe_app'@'%';
Grants for cafe_app@%
GRANT USAGE ON *.* TO `cafe_app`@`%`
GRANT SELECT, INSERT ON `cafe_practice`.* TO `cafe_app`@`%`

권한은 준 범위 그대로 빼야 한다. DB 전체(cafe_practice.*)에 준 SELECT를 테이블 하나에서만 빼려고 하면, 그 테이블 단위로 준 권한이 없으므로 오류가 난다.

1
2

REVOKE SELECT ON cafe_practice.menu FROM 'cafe_app'@'%';
-- ERROR 1147 (42000): There is no such grant defined for user 'cafe_app' on host '%' on table 'menu'

주의할 점: “DB 전체에서 테이블 하나만 빼고” 주고 싶다면, DB 전체에 준 뒤 하나를 REVOKE하는 방식은 통하지 않는다. 필요한 테이블마다 따로 GRANT한다.

WITH GRANT OPTION

WITH GRANT OPTION을 붙여 받은 사용자는 자신이 가진 권한을 다른 사용자에게 다시 줄 수 있다.

1
2
3

CREATE USER 'cafe_manager'@'localhost' IDENTIFIED BY 'dummy1234';
GRANT SELECT, UPDATE ON cafe_practice.menu TO 'cafe_manager'@'localhost' WITH GRANT OPTION;
SHOW GRANTS FOR 'cafe_manager'@'localhost';
Grants for cafe_manager@localhost
GRANT USAGE ON *.* TO `cafe_manager`@`localhost`
GRANT SELECT, UPDATE ON `cafe_practice`.`menu` TO `cafe_manager`@`localhost` WITH GRANT OPTION

cafe_manager로 접속해 아르바이트생에게 권한을 나눠 준다. 갖고 있지 않은 권한은 줄 수 없다.

1
2
3

GRANT SELECT ON cafe_practice.menu TO 'cafe_parttime'@'localhost';   -- 성공
GRANT DELETE ON cafe_practice.menu TO 'cafe_parttime'@'localhost';
-- ERROR 1142 (42000): DELETE command denied to user 'cafe_manager'@'localhost' for table 'menu'

이제 관리자(root)가 cafe_manager의 권한을 모두 빼앗는다. GRANT OPTION은 ALL PRIVILEGES에 포함되지 않으므로 함께 적는다.

1
2

REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'cafe_manager'@'localhost';
SHOW GRANTS FOR 'cafe_parttime'@'localhost';
Grants for cafe_parttime@localhost
GRANT USAGE ON *.* TO `cafe_parttime`@`localhost`
GRANT SELECT (`member_id`, `name`) ON `cafe_practice`.`member` TO `cafe_parttime`@`localhost`
GRANT SELECT ON `cafe_practice`.`menu` TO `cafe_parttime`@`localhost`

cafe_manager는 권한을 잃었지만, 그가 나눠 준 cafe_parttime의 메뉴 조회 권한은 남아 있다. MySQL은 권한을 누가 줬는지 추적하지 않아서 연쇄적으로 회수하지 않는다.

주의할 점: 표준 SQL(시험 문법)은 REVOKE 권한 ON 테이블 FROM 사용자 CASCADE;로 그 사용자가 다른 사람에게 준 권한까지 함께 회수하고, REVOKE GRANT OPTION FOR 권한 ON 테이블 FROM 사용자;로 권한은 두고 “넘겨주는 권한”만 뺀다. MySQL의 REVOKE에는 CASCADE가 없다.

역할(ROLE): 권한 묶음

직원이 늘어날 때마다 같은 권한 목록을 반복해서 주는 대신, 권한을 역할로 묶어 두고 역할을 준다. MySQL 8.0부터 지원한다.

1
2
3
4
5

7

CREATE ROLE 'cafe_role_read', 'cafe_role_write';
GRANT SELECT ON cafe_practice.* TO 'cafe_role_read';
GRANT INSERT, UPDATE, DELETE ON cafe_practice.* TO 'cafe_role_write';

CREATE USER 'cafe_intern'@'localhost' IDENTIFIED BY 'dummy1234';
GRANT 'cafe_role_read' TO 'cafe_intern'@'localhost';
SHOW GRANTS FOR 'cafe_intern'@'localhost';
Grants for cafe_intern@localhost
GRANT USAGE ON *.* TO `cafe_intern`@`localhost`
GRANT `cafe_role_read`@`%` TO `cafe_intern`@`localhost`

역할을 받았는데도 cafe_intern으로 접속하면 조회가 안 된다.

1

SELECT CURRENT_ROLE();
CURRENT_ROLE()
NONE
1
2

SELECT COUNT(*) AS 회원수 FROM cafe_practice.member;
-- ERROR 1142 (42000): SELECT command denied to user 'cafe_intern'@'localhost' for table 'member'

역할은 받는 것과 켜는 것이 따로다. 접속할 때 자동으로 켜질 역할을 SET DEFAULT ROLE로 정한다(세션 안에서 잠깐 켤 때는 SET ROLE '역할';).

1

SET DEFAULT ROLE 'cafe_role_read' TO 'cafe_intern'@'localhost';   -- root가 실행

다시 접속하면 역할이 켜져 있다.

1

SELECT CURRENT_ROLE();
CURRENT_ROLE()
`cafe_role_read`@`%`

회원수

DELETE FROM cafe_practice.member;
-- ERROR 1142 (42000): DELETE command denied to user 'cafe_intern'@'localhost' for table 'member'

쓰기 권한까지 필요해지면 GRANT 'cafe_role_write' TO 'cafe_intern'@'localhost';처럼 역할 하나만 더 주면 된다. 역할도 mysql.user에 호스트가 %인 계정처럼 저장된다.

DROP USER, DROP ROLE

Oracle은 계정에 호스트가 없고(CREATE USER 이름 IDENTIFIED BY 비밀번호), 접속 권한부터 GRANT CREATE SESSION으로 따로 줘야 한다.

복습 문제

  1. 'cafe_staff'@'localhost'와 'cafe_staff'@'%'가 둘 다 있을 때, 두 계정은 같은 계정인지 쓰고, 각각 어디에서 접속할 수 있는지 쓰시오.
  2. 계산대용 계정 cafe_cashier(서버와 같은 컴퓨터에서만 접속, 비밀번호 dummy1234)를 만들고, 메뉴(cafe_practice.menu)는 조회만, 회원(cafe_practice.member)은 조회와 등록만 할 수 있게 하는 SQL을 쓰시오. 이 계정으로 회원 등급을 수정하면 어떻게 되는지도 쓰시오.
  3. 2번의 cafe_cashier에게 이어서 다음을 실행했다. 이제 cafe_cashier가 메뉴와 회원을 조회할 수 있는지 쓰시오.
    1
2

    GRANT SELECT ON cafe_practice.* TO 'cafe_cashier'@'localhost';
REVOKE SELECT ON cafe_practice.* FROM 'cafe_cashier'@'localhost';
  4. A가 WITH GRANT OPTION으로 받은 SELECT 권한을 B에게 줬다. 그 뒤 관리자가 A의 권한을 회수했다. MySQL에서 B의 권한은 어떻게 되는지 쓰고, 표준 SQL에서 B의 권한까지 함께 회수하는 문장의 끝에 붙는 키워드를 쓰시오.
  5. 역할 cafe_role_read를 받은 사용자가 접속 직후 조회를 하면 권한 오류가 난다. 이유와 해결 방법을 쓰시오.
정답과 해설

1. 다른 계정이다. MySQL 계정은 사용자 이름과 호스트의 쌍이라, 비밀번호와 권한도 따로 가진다. 'cafe_staff'@'localhost'는 DB 서버와 같은 컴퓨터에서만, 'cafe_staff'@'%'는 어디서든 접속할 수 있다. 같은 컴퓨터에서 접속하면 더 구체적인 'cafe_staff'@'localhost' 계정이 먼저 선택되므로, 'cafe_staff'@'%'의 비밀번호로 서버 컴퓨터에서 로그인하면 ERROR 1045 (28000): Access denied로 거부된다.

2. 계정을 먼저 만들고 테이블마다 권한을 준다.

1
2
3
4

CREATE USER 'cafe_cashier'@'localhost' IDENTIFIED BY 'dummy1234';
GRANT SELECT ON cafe_practice.menu TO 'cafe_cashier'@'localhost';
GRANT SELECT, INSERT ON cafe_practice.member TO 'cafe_cashier'@'localhost';
SHOW GRANTS FOR 'cafe_cashier'@'localhost';
Grants for cafe_cashier@localhost
GRANT USAGE ON *.* TO `cafe_cashier`@`localhost`
GRANT SELECT, INSERT ON `cafe_practice`.`member` TO `cafe_cashier`@`localhost`
GRANT SELECT ON `cafe_practice`.`menu` TO `cafe_cashier`@`localhost`

UPDATE 권한이 없으므로 등급 수정은 거부된다.

1
2

UPDATE cafe_practice.member SET grade = 'VIP' WHERE member_id = 101;
-- ERROR 1142 (42000): UPDATE command denied to user 'cafe_cashier'@'localhost' for table 'member'

3. 둘 다 조회할 수 있다. 권한은 범위(전역·DB·테이블·열)마다 따로 저장된다. REVOKE는 방금 DB 단위로 준 SELECT만 빼고, 2번에서 테이블 단위로 준 권한은 건드리지 않는다. SHOW GRANTS도 2번의 결과와 같다. 확인한 뒤 DROP USER 'cafe_cashier'@'localhost';로 지운다.

4. MySQL에서는 B의 권한이 그대로 남는다. MySQL은 권한을 누가 줬는지 추적하지 않는다. 표준 SQL은 REVOKE SELECT ON 테이블 FROM A CASCADE;처럼 CASCADE를 붙여 A가 넘겨준 권한까지 연쇄적으로 회수한다.

5. 역할은 받기만 하고 켜지지 않았기 때문이다(CURRENT_ROLE()이 NONE). SET DEFAULT ROLE 'cafe_role_read' TO '사용자'@'호스트';로 접속할 때 자동으로 켜지게 하거나, 세션 안에서 SET ROLE 'cafe_role_read';를 실행한다.
