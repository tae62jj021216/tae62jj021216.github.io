[DB] 03. 관계 모델과 키, 무결성 제약조건

관계형 데이터베이스는 데이터를 릴레이션(테이블)으로 표현하고, 키로 행을 구별하며, 무결성 제약조건으로 잘못된 데이터가 들어오지 못하게 막는다. 이 글에서는 스키마와 인스턴스, 릴레이션의 특성, 다섯 가지 키, 세 가지 무결성 제약조건을 정리한다.

예제는 00편의 cafedb를 쓴다. 제약조건을 일부러 어기는 예제는 cafedb를 복사한 연습 DB cafe_practice에서 실행한다. SQL 문법은 8편부터 다룬다. 여기서는 결과만 보면 된다. MySQL 8.4에서 실행한 결과다.

릴레이션 = 스키마 + 인스턴스

릴레이션은 두 부분으로 이루어진다.

구분뜻다른 이름변화
릴레이션 스키마릴레이션 이름, 속성 이름, 각 속성의 도메인내포(intension)거의 바뀌지 않는다
릴레이션 인스턴스어느 시점에 들어 있는 튜플들의 집합외연(extension)삽입·수정·삭제할 때마다 바뀐다

category의 스키마는 category(category_id: INT, name: VARCHAR(20), parent_id: INT)이고, 지금 이 순간의 인스턴스는 (1, 음료, NULL), (2, 커피, 1), … (8, 구움과자, 6)의 8개 튜플이다. 새 카테고리를 추가하면 인스턴스(카디널리티)는 바뀌지만 스키마는 그대로다. 뒤에서 볼 키와 무결성 제약조건은 스키마에 정의되고, 앞으로 생길 모든 인스턴스가 지켜야 하는 규칙이다.

릴레이션의 특성

이론상의 릴레이션은 튜플의 집합이라서 다음 네 가지 성질을 가진다.

특성뜻SQL 테이블에서는
튜플의 유일성똑같은 튜플이 두 번 있을 수 없다기본키가 없으면 같은 행이 여러 번 들어간다 (event_2025에 같은 행을 또 넣으면 들어간다)
튜플의 무순서성튜플 사이에 순서가 없다ORDER BY가 없으면 순서가 보장되지 않는다
속성의 무순서성속성 사이에 순서가 없다 (이름으로 구별)SELECT *, 열 목록 없는 INSERT는 정의된 열 순서를 따른다
속성의 원자성한 칸에는 더 나눌 수 없는 값 하나만 들어간다설계로 지킨다. 주문의 메뉴를 한 칸에 몰아 넣지 않고 order_item에 한 행씩 담는다 (1NF, 7편)

주의할 점: 시험에서 릴레이션의 특성을 물으면 이론상의 릴레이션 기준으로 답한다. “튜플은 중복될 수 없다”, “튜플과 속성에는 순서가 없다”, “속성 값은 원자값이다”가 정답이다. SQL 테이블이 중복 행을 허용한다는 것은 별개의 사실이다.

키의 조건과 종류

키(Key)는 튜플을 서로 구별하는 데 쓰는 속성(들)의 집합이다. 키를 판단할 때는 두 조건을 본다.

  • 유일성(Uniqueness): 그 속성 값의 조합이 같은 튜플이 둘 이상 없다.
  • 최소성(Minimality): 속성을 하나라도 빼면 유일성이 깨진다. 꼭 필요한 속성만으로 이루어져 있다.
키조건cafedb 예
슈퍼키 (Super Key)유일성만 만족menu의 {menu_id}, {name}, {menu_id, price}, {menu_id, name} …
후보키 (Candidate Key)유일성과 최소성을 모두 만족menu의 {menu_id}, {name}
기본키 (Primary Key)후보키 중에서 대표로 고른 하나menu의 menu_id
대체키 (Alternate Key)기본키로 뽑히지 않은 나머지 후보키menu의 name
외래키 (Foreign Key)다른(또는 같은) 릴레이션의 기본키를 참조하는 속성menu.category_id → category.category_id

menu로 보는 슈퍼키와 후보키

메뉴 번호도, 메뉴 이름(UNIQUE)도 겹치지 않는다.

  • {menu_id, price}는 유일하므로 슈퍼키지만, price를 빼도 유일하므로 최소성을 어긴다. 후보키가 아니다.
  • {menu_id}와 {name}은 더 뺄 속성이 없으므로 둘 다 후보키다. 짧고 바뀌지 않는 menu_id를 기본키로 골랐고, 남은 name은 대체키다.

후보키는 모두 슈퍼키이지만, 슈퍼키가 모두 후보키인 것은 아니다.

order_item으로 보는 복합 후보키

19행인 order_item에서 order_id는 12종류, menu_id는 11종류뿐이라 어느 하나만으로는 행을 구별할 수 없고, 두 속성을 합친 {order_id, menu_id}는 19종류로 모든 행을 구별한다(종류 수를 세는 SQL은 12·13편에서 다룬다). 하나라도 빼면 유일성이 깨지므로 최소성도 만족한다. 이 후보키가 복합 기본키다.

주의할 점: 인스턴스로는 키가 아님을 보일 수는 있어도 키임을 증명하지는 못한다. member의 이름은 지금 모두 다르지만 동명이인이 가입할 수 있어 후보키가 아니다. 또 복합키(속성 두 개 이상)와 슈퍼키(유일성만 만족)는 다른 말이다. {menu_id}는 속성이 하나인 슈퍼키이고, {order_id, menu_id}는 복합키이면서 후보키다.

CREATE TABLE에서 PRIMARY KEY는 기본키, UNIQUE(+ NOT NULL)는 대체키, FOREIGN KEY는 외래키를 선언한다. 슈퍼키와 후보키는 DBMS에 선언하는 대상이 아니라 설계할 때 따지는 개념이다.

외래키

외래키는 다른 릴레이션의 기본키(또는 후보키)를 참조해 두 릴레이션을 연결한다. 참조하는 쪽을 자식(참조 릴레이션), 참조되는 쪽을 부모(피참조 릴레이션)라고 부른다.

  • member.referrer_id처럼 자기 자신의 기본키를 참조하는 외래키도 있다(추천인도 회원이다).
  • 외래키는 중복될 수 있고(회원 한 명이 주문 여러 건), 허용하면 NULL일 수도 있다(비회원 주문).
  • order_item.order_id처럼 기본키의 일부이면서 외래키인 속성도 있다.

무결성 제약조건

무결성(Integrity)은 데이터가 정확하고 서로 모순되지 않는 상태다. 이를 지키려고 스키마에 정의하는 규칙이 무결성 제약조건이고, DBMS는 규칙을 어기는 삽입·수정·삭제를 거부한다.

제약조건규칙SQL로 거는 방법
개체 무결성기본키는 NULL일 수 없고 중복될 수 없다PRIMARY KEY
참조 무결성외래키 값은 NULL이거나, 부모 릴레이션의 기본키 값 중 하나여야 한다FOREIGN KEY … REFERENCES
도메인 무결성속성 값은 그 속성의 도메인(타입, 범위, 형식)에 속해야 한다데이터 타입, CHECK, NOT NULL

시험에는 이 밖에 고유 무결성(UNIQUE 속성 값은 서로 달라야 한다. menu.name에 이미 있는 이름을 넣으면 ERROR 1062), NULL 무결성(NOT NULL. 도메인 무결성에 넣기도 한다), 키 무결성(릴레이션에는 키가 적어도 하나 있어야 한다), 사용자 정의 무결성(업무 규칙에 맞아야 한다)이 따로 나온다.

아래는 cafe_practice에서 세 가지 규칙을 일부러 어겨 본 결과다.

개체 무결성: 기본키는 NULL도 중복도 안 된다

USE cafe_practice;

INSERT INTO member (member_id, name, joined_on) VALUES (NULL, '고객A', '2026-09-01');
-- ERROR 1048 (23000): Column 'member_id' cannot be null

INSERT INTO member (member_id, name, joined_on) VALUES (101, '고객A', '2026-09-01');
-- ERROR 1062 (23000): Duplicate entry '101' for key 'member.PRIMARY'

기본키가 NULL이면 튜플을 가리킬 수 없고, 중복이면 구별할 수 없기 때문이다. 복합 기본키는 구성하는 속성 모두가 NULL이 될 수 없다.

참조 무결성: 없는 부모를 가리키면 안 된다

없는 회원 번호로 주문을 넣으면 거부된다.

1
2
3

INSERT INTO orders (order_id, member_id, store, ordered_at)
VALUES (13, 999, '본점', '2026-09-01 10:00:00');
-- ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`cafe_practice`.`orders`, CONSTRAINT `orders_ibfk_1` ...)

외래키가 NULL인 비회원 주문은 “아무도 가리키지 않는다”는 뜻이라 허용된다.

주문이 남아 있는 회원을 지우거나 번호를 바꾸는 것도 자식이 사라진 부모를 가리키게 되므로 거부된다.

1
2

DELETE FROM member WHERE member_id = 106;
-- ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`cafe_practice`.`orders`, CONSTRAINT `orders_ibfk_1` ...)

거부 대신 자식도 함께 지우는(CASCADE) 식으로 다른 동작을 정할 수도 있다. order_item.order_id가 그렇게 정의돼 있어서 주문을 지우면 그 주문의 order_item 행도 함께 사라진다. 이런 옵션은 8편에서 다룬다.

도메인 무결성: 값이 도메인 안에 있어야 한다

타입이 맞지 않는 값, 존재하지 않는 날짜('2026-02-30'), CHECK 조건을 어기는 값, NOT NULL 열에 값이 없는 경우는 모두 도메인 무결성 위반이다.

INSERT INTO menu VALUES (12, '아이스티', 3, '4000원', FALSE, '2026-09-01');
-- ERROR 1265 (01000): Data truncated for column 'price' at row 1

INSERT INTO menu VALUES (12, '아이스티', 3, -500, FALSE, '2026-09-01');
-- ERROR 3819 (HY000): Check constraint 'menu_chk_1' is violated.

주의할 점: MySQL은 sql_mode의 엄격 모드(STRICT_TRANS_TABLES, 8.x 기본값)일 때만 '4000원'을 거부한다. 엄격 모드를 끄면 '4000원'을 4000으로 잘라 넣고 경고만 남긴다. CHECK는 엄격 모드와 상관없이 검사하는데, MySQL 8.0.16부터 실제로 검사하고, 그 전에는 무시했다.

복습 문제

  1. 릴레이션 coupon(coupon_code, member_id, issued_on, amount)가 있다. 쿠폰 코드는 전부 다르고, 한 회원은 같은 날 쿠폰을 한 장까지만 받는다. 다음 중 후보키를 모두 고르고, 슈퍼키이지만 후보키가 아닌 것을 하나 쓰시오.
    ① {coupon_code} ② {member_id} ③ {member_id, issued_on} ④ {coupon_code, amount}
  2. 다음 설명 중 틀린 것을 고르고 바르게 고치시오.
    • ① 외래키는 NULL 값을 가질 수 있다.
    • ② 한 릴레이션에서 후보키는 여러 개일 수 있다.
    • ③ 슈퍼키는 두 개 이상의 속성으로 이루어진 키를 말한다.
    • ④ 개체 무결성에 따라 기본키를 이루는 속성은 NULL을 가질 수 없다.
  3. 본문 예제에 이어 cafe_practice에서 다음 SQL을 순서대로 실행할 때 각각 성공하는지, 실패한다면 어떤 무결성 제약조건 위반인지 쓰시오. (menu에는 menu_id 1~11이 있고, category_id 99는 없다.)

  4. 릴레이션의 특성 네 가지를 쓰고, 기본키가 없는 SQL 테이블이 그중 어떤 특성을 어길 수 있는지 쓰시오.
정답과 해설
  1. 후보키: ① {coupon_code}, ③ {member_id, issued_on}. 둘 다 유일하고 더 뺄 속성이 없다(③에서 어느 하나만 남기면 겹친다). ④ {coupon_code, amount}는 amount를 빼도 유일하므로 슈퍼키이지만 후보키가 아니다. ② {member_id}는 유일성부터 만족하지 않는다.
  2. ③이 틀렸다. 두 개 이상의 속성으로 이루어진 키는 복합키다. 슈퍼키는 속성 개수와 상관없이 유일성을 만족하는 속성 집합이다.
  3. 실제로 실행한 결과다.
    • (가) 실패, 참조 무결성 위반. 카테고리 99가 없다(ERROR 1452).
    • (나) 실패, 도메인 무결성 위반. CHECK (price > 0)에 0은 들어가지 않는다(ERROR 3819).
    • (다) 성공. 12번 메뉴 ‘레몬 에이드’가 추가된다.
    • (라) 실패, 개체 무결성 위반. 복합 기본키의 일부인 menu_id가 NULL이다(ERROR 1048).
  4. 튜플의 유일성, 튜플의 무순서성, 속성의 무순서성, 속성의 원자성. 기본키가 없는 SQL 테이블은 똑같은 행을 여러 번 저장할 수 있으므로 튜플의 유일성을 어길 수 있다.
