시리즈의 마지막 글이다. 5편에서 만든 쇼핑몰 크롤러의 결과를 CSV가 아니라 MySQL 테이블에 바로 넣는다. 저장 방식 두 가지를 비교하고, 같은 크롤러를 다시 돌릴 때 생기는 문제를 해결한 뒤, pandas로 다시 꺼내 분석한다.

5편의 get_soup(), won(), parse_product()와 10편의 pymysql 연결(DB)을 그대로 쓴다. SQLAlchemy는 pip install sqlalchemy로 설치한다. 결과는 Python 3.12, PyMySQL 2.2, SQLAlchemy 2.1, pandas 3.0, MySQL 8.4에서 확인했다.

import pymysql

conn = pymysql.connect(**DB, database="cafe_crawl")
with conn.cursor() as cur:
    cur.execute("DROP TABLE IF EXISTS product")
    cur.execute("""
    CREATE TABLE product (
        id          CHAR(4)       PRIMARY KEY,
        name        VARCHAR(100)  NOT NULL,
        category    VARCHAR(20),
        price       INT           NOT NULL,
        sale_price  INT,
        discount    INT           DEFAULT 0,
        soldout     BOOLEAN       DEFAULT FALSE,
        rating      DECIMAL(2,1),
        reviews     INT,
        crawled_at  DATETIME      DEFAULT CURRENT_TIMESTAMP
    )""")
conn.commit()
  • sale_price는 세일하지 않는 상품이 있어 NULL을 허용한다(NOT NULL을 붙이지 않음).
  • crawled_at은 언제 모은 값인지 남긴다. 값을 넘기지 않으면 넣는 시각이 들어간다.
  • 가격은 5편에서 이미 int로 바꿨으므로 INT로 저장한다. 글자 "18,000원"을 그대로 저장하면 SQL에서 정렬·합계를 낼 수 없다.

import time

def save_per_page(conn, urls):
    for url in urls:
        rows = [to_tuple(parse_product(li)) for li in get_soup(url).select("li.product")]
        try:
            with conn.cursor() as cur:
                n = cur.executemany(INSERT, rows)
            conn.commit()
            print(url.rsplit("/", 1)[1], n)
        except pymysql.MySQLError as e:
            conn.rollback()
            print(url.rsplit("/", 1)[1], "실패:", e)
        time.sleep(1)

save_per_page(conn, urls)            # urls: 5편의 list-1 ~ list-4 주소
with conn.cursor() as cur:
    cur.execute("SELECT COUNT(*), SUM(soldout), SUM(sale_price IS NOT NULL) FROM product")
    print(cur.fetchone())

def crawl_all(urls):
    rows = []
    for url in urls:
        rows += [to_tuple(parse_product(li)) for li in get_soup(url).select("li.product")]
        time.sleep(1)
    return rows

all_rows = crawl_all(urls)
with conn.cursor() as cur:
    cur.execute("DELETE FROM product")          # 비교를 위해 비우고 다시 넣는다
    print(cur.executemany(INSERT, all_rows))
conn.commit()

다시 돌리면: 기본키 충돌

크롤러는 보통 매일처럼 반복해 돌린다. 이미 30개가 든 상태에서 방식 1을 한 페이지만 다시 돌려 본다.

save_per_page(conn, urls[:1])

1

list-1.html 실패: (1062, "Duplicate entry 'p001' for key 'product.PRIMARY'")

같은 id가 이미 있어 INSERT가 실패했다. 다시 모은 값으로 있으면 고치고, 없으면 넣으려면 MySQL의 INSERT ... ON DUPLICATE KEY UPDATE(업서트)를 쓴다.

1
2
3

UPSERT = INSERT + """ AS new
ON DUPLICATE KEY UPDATE price = new.price, sale_price = new.sale_price, discount = new.discount,
    soldout = new.soldout, rating = new.rating, reviews = new.reviews"""

AS new는 “새로 넣으려던 행”에 붙인 별칭이다(MySQL 8.0.19부터). 기본키가 겹치면 INSERT 대신 UPDATE 부분이 실행된다. 확인을 위해 DB에서 p002의 가격을 일부러 틀리게 바꾼 뒤 다시 넣는다.

p002의 가격이 사이트 값(15,000원)으로 돌아왔고, 행은 여전히 30개다. 영향받은 행 수가 2인 것은 MySQL이 업서트에서 “새로 넣음 1, 고침 2, 그대로 0”으로 세기 때문이다. 나머지 29개는 값이 같아 0으로 세어졌다.

주의할 점: 수집 시각도 갱신하려고 UPDATE 목록에 crawled_at = CURRENT_TIMESTAMP를 넣으면, 시각은 돌릴 때마다 달라지므로 30행 모두 “고침”이 되어 60이 나온다(2초 뒤에 다시 돌려 확인했다). 어떤 상품의 값이 실제로 바뀌었는지 알고 싶다면 updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP 열을 두면 된다. 값이 바뀐 행만 시각이 갱신된다.

복습 문제

  1. sale_price 열에 NOT NULL을 붙이면 어떤 상품을 넣을 때 오류가 나는가?
  2. 크롤링을 200페이지 하다가 150페이지에서 네트워크가 끊겼다. 방식 1과 방식 2의 DB 상태를 각각 쓰시오.
  3. 업서트를 실행했더니 영향받은 행 수가 5였다. 새로 들어간 행이 1개라면, 값이 바뀐 행은 몇 개인가?
  4. pd.read_sql에 pymysql 연결을 넘겼을 때 경고가 나는 이유와 해결 방법을 쓰시오.
  5. to_sql(..., if_exists="append")로 같은 DataFrame을 두 번 넣으면 어떻게 되는가? 이유는 무엇인가?
정답과 해설
  1. 세일하지 않는 상품. sale_price가 None(NULL)이다.
  2. 방식 1은 149페이지(또는 실패한 페이지 직전)까지 저장되어 있다. 방식 2는 아무것도 저장되지 않는다(모은 결과가 메모리에만 있다가 사라진다).
  3. 2개. 새로 넣음 1 + 고침 2 × 2 = 5. 값이 같은 행은 0으로 센다.
  4. pandas가 공식 지원하는 연결은 SQLAlchemy(엔진·연결)와 sqlite3다. create_engine으로 엔진을 만들어 넘긴다.
  5. 같은 행이 두 번 쌓인다. to_sql이 만든 테이블에는 기본키가 없어 중복을 막지 못한다.
