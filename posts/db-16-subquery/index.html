[DB] 16. 서브쿼리

15편의 조인이 테이블을 옆으로 이어 붙였다면, 서브쿼리(subquery)는 SQL 문 안에 괄호로 넣은 또 하나의 SELECT다. “평균보다 비싼 메뉴”처럼 조건에 쓸 값을 먼저 구해야 할 때, 쿼리 두 번을 하나로 합쳐 준다. 이 글에서는 서브쿼리를 위치와 결과 행 수로 나누고, IN·ANY·ALL·EXISTS, 다중 열·상관 서브쿼리, NOT IN과 NULL 함정을 정리한다.

예제는 00편의 cafedb를 쓴다. MySQL 8.4에서 실행한 결과다.

서브쿼리의 기본 형태

“메뉴 평균 가격보다 비싼 메뉴”를 찾으려면 평균을 먼저 알아야 한다. 평균을 구하는 쿼리를 괄호로 감싸 조건 자리에 넣는다.

1
2
3

SELECT name, price FROM menu
WHERE price > (SELECT AVG(price) FROM menu)   -- 5136.3636
ORDER BY price DESC, menu_id;

(일부 행)

바깥쪽 쿼리를 메인 쿼리(외부 쿼리), 괄호 안을 서브쿼리(내부 쿼리)라고 한다. 서브쿼리는 반드시 괄호로 감싼다.

위치에 따른 분류

위치이름결과 형태
SELECT 절스칼라 서브쿼리한 행 한 열(값 하나)
FROM 절인라인 뷰(파생 테이블)테이블처럼 쓰는 결과 집합
WHERE·HAVING 절중첩 서브쿼리조건 비교에 쓰는 값 또는 목록

스칼라 서브쿼리: SELECT 절

SELECT 절의 서브쿼리는 행마다 값 하나를 돌려줘야 한다. 회원별 마지막 주문 시각을 붙여 보자.

1

4
5

SELECT m.member_id, m.name,
       (SELECT MAX(o.ordered_at) FROM orders o
        WHERE o.member_id = m.member_id) AS last_order
FROM member m
ORDER BY m.member_id;

(일부 행)

주문이 없는 팥쥐는 서브쿼리 결과가 없어서 NULL이 된다. 스칼라 서브쿼리는 결과가 0행이면 NULL, 2행 이상이면 오류다.

인라인 뷰: FROM 절

FROM 절의 서브쿼리는 결과를 임시 테이블처럼 쓴다. “주문별 금액 → 지점별 평균”처럼 집계를 두 번 해야 할 때 쓴다.

1
2
3
4
5
6
7
8

SELECT o.store, COUNT(*) AS order_cnt, ROUND(AVG(t.amount)) AS avg_amount
FROM orders o
JOIN (SELECT oi.order_id, SUM(oi.qty * m.price) AS amount
      FROM order_item oi JOIN menu m ON m.menu_id = oi.menu_id
      GROUP BY oi.order_id) AS t
  ON t.order_id = o.order_id
GROUP BY o.store
ORDER BY avg_amount DESC;
storeorder_cntavg_amount
강변점413250
공원점312167
본점510800

인라인 뷰에는 반드시 별칭(AS t)을 붙여야 한다. 빼면 ERROR 1248 (42000): Every derived table must have its own alias가 난다(복습 문제 4). 이 인라인 뷰에 이름을 붙여 쿼리 앞으로 빼낸 것이 17편의 CTE(WITH)다.

Oracle은 인라인 뷰 별칭을 생략해도 되지만, 테이블 별칭 앞에 AS를 쓰면 오류다.

가장 흔한 WHERE 절의 중첩 서브쿼리는 결과 행 수에 따라 나눠 본다.

단일행 서브쿼리

결과가 한 행인 서브쿼리다. =, <>, >, >=, <, <= 같은 단일행 비교 연산자와 쓴다.

1
2
3

SELECT name, price FROM menu
WHERE price = (SELECT price FROM menu WHERE name = '카페라떼')   -- 카페라떼, 콜드브루 (5000)
ORDER BY menu_id;

서브쿼리가 여러 행을 돌려주는데 =를 쓰면 오류다. 콜드브루 카테고리(5)에는 메뉴가 두 개 있다.

1
2
3

SELECT name, price FROM menu
WHERE price = (SELECT price FROM menu WHERE category_id = 5);
-- ERROR 1242 (21000): Subquery returns more than 1 row

주의할 점: 데이터가 적을 때 우연히 한 행만 나와 잘 돌던 쿼리도 데이터가 늘면 오류를 낸다. 여러 행일 수 있으면 IN을 쓰거나 MAX·MIN으로 한 행을 보장한다.

다중행 서브쿼리: IN, ANY, ALL

결과가 여러 행일 수 있는 서브쿼리에는 다중행 연산자를 쓴다.

IN

목록 중 하나와 같으면 참이다. 위의 오류 쿼리를 IN으로 고친다(콜드브루 카테고리 자신은 뺀다).

1
2
3
4

SELECT name, price FROM menu
WHERE price IN (SELECT price FROM menu WHERE category_id = 5)   -- 5000, 5500
  AND category_id <> 5
ORDER BY menu_id;
nameprice
카페라떼5000
바닐라라떼5500
말차라떼5500

ANY와 ALL

비교 연산자 뒤에 붙여 쓴다. ANY는 서브쿼리 결과 중 하나라도 만족하면, ALL은 모두 만족하면 참이다. 에스프레소 카테고리(4)의 가격은 4500, 5000, 5500이다.

1
2
3
4

SELECT name, price FROM menu
WHERE category_id <> 4
  AND price > ALL (SELECT price FROM menu WHERE category_id = 4)
ORDER BY price, menu_id;
nameprice
딸기 에이드6000
치즈케이크6500
초코케이크6500

> ALL은 “가장 비싼 것(5500)보다 비싸야” 한다. ALL을 ANY로 바꾸면 “가장 싼 것(4500)보다 비싸면” 되므로 콜드브루(5000)·콜드브루 라떼·말차라떼(5500)까지 6개가 나온다. 최솟값·최댓값으로 바꿔 외우면 쉽다.

표현같은 뜻
> ANY (...)> MIN(...)
> ALL (...)> MAX(...)
< ANY (...)< MAX(...)
< ALL (...)< MIN(...)
= ANY (...)IN (...)
<> ALL (...)NOT IN (...)

SOME은 ANY와 같은 뜻이다.

주의할 점: 서브쿼리 결과가 0행이면 ALL은 무조건 참, ANY는 무조건 거짓이다. 없는 카테고리(99)로 price > ALL (...)을 쓰면 메뉴 11개가 전부 나오지만, > (SELECT MAX(price) ...)는 MAX가 NULL이라 0개다. 표의 “같은 뜻”은 결과가 있고 NULL이 없을 때만 성립한다.

다중 열 서브쿼리

서브쿼리가 열 두 개 이상을 돌려주면, 메인 쿼리에서도 열을 괄호로 묶어 짝으로 비교한다. “지점마다 가장 먼저 들어온 주문”은 지점과 시각이 둘 다 맞아야 한다.

1
2
3
4

SELECT order_id, store, ordered_at FROM orders
WHERE (store, ordered_at) IN (SELECT store, MIN(ordered_at)
                              FROM orders GROUP BY store)
ORDER BY order_id;
order_idstoreordered_at
1본점2026-08-01 08:12:00
3강변점2026-08-02 09:05:00
5공원점2026-08-05 10:00:00

ordered_at만 비교하면 다른 지점의 첫 주문과 시각이 같은 주문도 걸릴 수 있다.

다중 열 IN은 MySQL과 Oracle 모두 지원하지만, SQL Server는 지원하지 않아 EXISTS로 바꿔 쓴다.

상관 서브쿼리와 비상관 서브쿼리

지금까지의 WHERE 절 서브쿼리는 메인 쿼리와 상관없이 한 번 실행되는 비상관 서브쿼리다. 서브쿼리 안에서 메인 쿼리의 열을 참조하면 상관 서브쿼리가 되어, 메인 쿼리의 행마다 그 값을 받아 다시 계산한다. “자기 카테고리 평균보다 비싼 메뉴”가 대표적인 예다.

1
2
3
4
5

SELECT m.name, m.price, m.category_id
FROM menu m
WHERE m.price > (SELECT AVG(s.price) FROM menu s
                 WHERE s.category_id = m.category_id)   -- 바깥 행의 카테고리
ORDER BY m.menu_id;
namepricecategory_id
바닐라라떼55004
콜드브루 라떼55005
딸기 에이드60003
밤 마들렌35008

케이크(7)는 두 메뉴가 모두 평균(6500)과 같아서 하나도 나오지 않는다.

비상관 서브쿼리는 떼어 내 단독으로 실행할 수 있지만, 상관 서브쿼리는 바깥 별칭(m)이 없어 단독으로 실행하면 오류다. 앞의 “회원별 마지막 주문 시각”도 m.member_id를 참조하는 상관 서브쿼리다.

EXISTS

EXISTS (서브쿼리)는 서브쿼리 결과가 한 행이라도 있으면 참이다. 값은 보지 않으므로 SELECT 1, SELECT * 무엇을 써도 같다. 강변점에서 주문한 적 있는 회원을 IN과 EXISTS로 각각 찾아 보자.

1
2
3
4
5
6
7
8

SELECT name FROM member
WHERE member_id IN (SELECT member_id FROM orders WHERE store = '강변점')
ORDER BY member_id;

SELECT m.name FROM member m
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.member_id = m.member_id AND o.store = '강변점')
ORDER BY m.member_id;

두 쿼리 모두 이몽룡, 놀부를 돌려준다.

구분INEXISTS
판단 기준서브쿼리 결과 값과 같은지서브쿼리 결과 행이 있는지
주로 쓰는 형태비상관 서브쿼리상관 서브쿼리
서브쿼리의 NULL결과에 영향을 준다(아래 NOT IN)영향을 주지 않는다

옵티마이저가 두 형태를 서로 바꿔 실행하기도 해서 성능은 “항상 어느 쪽이 빠르다”고 말할 수 없다.

NOT IN과 NULL 함정

“한 번도 주문하지 않은 회원”을 NOT IN으로 찾으면 결과가 하나도 나오지 않는다.

1
2
3

SELECT name FROM member
WHERE member_id NOT IN (SELECT member_id FROM orders);
-- 결과 없음 (Empty set)

주문이 없는 팥쥐(108)가 있는데도 빈 결과다. 원인은 비회원 주문의 member_id인 NULL이다. NOT IN은 목록의 모든 값과 <>로 비교해 AND로 묶은 것과 같다.

1
2
3
4

108 NOT IN (101, 102, NULL, ...)
= 108 <> 101 AND 108 <> 102 AND 108 <> NULL AND ...
= TRUE AND TRUE AND UNKNOWN AND ...
= UNKNOWN   → WHERE에서 걸러진다

TRUE AND UNKNOWN은 UNKNOWN이다. IN은 같은 값을 찾으면 참이 되지만(101 IN (101, NULL)은 1), NOT IN은 목록에 NULL이 하나라도 있으면 절대 참이 될 수 없다. 고치는 방법은 두 가지다. NOT EXISTS는 행의 존재만 보므로 NULL에 영향을 받지 않는다.

1
2
3
4
5

SELECT m.name FROM member m
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.member_id = m.member_id);

SELECT name FROM member
WHERE member_id NOT IN (SELECT member_id FROM orders WHERE member_id IS NOT NULL);

두 쿼리 모두 팥쥐 한 명을 돌려준다.

주의할 점: NOT IN (서브쿼리)를 쓸 때는 서브쿼리 열이 NULL을 허용하는지 먼저 본다. 허용한다면 NOT EXISTS를 쓰거나 서브쿼리에 IS NOT NULL 조건을 넣는다. 이 동작은 표준 SQL의 3값 논리에서 나온 것이라 Oracle도 똑같다.

서브쿼리와 조인 비교

강변점 주문 회원을 member JOIN orders로 찾으면 강변점 주문이 두 건인 이몽룡이 두 번 나온다. 조인은 짝이 맞는 행을 모두 만들고, IN·EXISTS는 메인 쿼리의 행을 거르기만 하기 때문이다. 다른 테이블의 열도 보여 줘야 하면 조인, 조건 검사만 필요하면 서브쿼리가 자연스럽다.

복습 문제

  1. 다음 쿼리의 서브쿼리 ①, ②를 위치(스칼라 / 인라인 뷰 / 중첩)와 상관 여부로 분류하시오.
    1
2
3

    SELECT t.store, t.cnt
FROM (SELECT store, COUNT(*) AS cnt FROM orders GROUP BY store) AS t      -- ①
WHERE t.cnt >= (SELECT COUNT(*) FROM orders WHERE store = '공원점');       -- ②
  2. 다음 쿼리의 결과를 예측하고 이유를 설명하시오. 원래 의도(“다른 회원을 추천한 적 없는 회원 이름”)대로 고치시오.
    1
2

    SELECT COUNT(*) FROM member
WHERE member_id NOT IN (SELECT referrer_id FROM member);
  3. 카테고리마다 가장 비싼 메뉴의 카테고리 번호, 이름, 가격을 상관 서브쿼리로 조회하시오. 가장 비싼 메뉴가 여럿이면 모두 보여 준다.
  4. 다음 쿼리가 실패하는 이유를 쓰고 고치시오.
    1
2
3

    SELECT AVG(cnt)
FROM (SELECT member_id, COUNT(*) AS cnt FROM orders
      WHERE member_id IS NOT NULL GROUP BY member_id);
정답과 해설

1. ①은 FROM 절에 있으므로 인라인 뷰이고, 바깥 열을 참조하지 않으므로 비상관이다. ②는 WHERE 절의 중첩 서브쿼리이고, 역시 바깥 열(t.store 등)을 참조하지 않으므로 비상관 단일행 서브쿼리다.

2. 결과는 0이다. referrer_id에는 추천인이 없는 회원의 NULL이 들어 있어서, NOT IN 목록에 NULL이 섞이면 모든 비교가 UNKNOWN이 된다. NOT EXISTS로 고친다.

1
2
3

SELECT m.name FROM member m
WHERE NOT EXISTS (SELECT 1 FROM member r WHERE r.referrer_id = m.member_id)
ORDER BY m.member_id;

결과는 성춘향, 흥부, 놀부, 콩쥐, 팥쥐다. 추천인으로 등장하는 101, 103, 104를 뺀 5명이다. WHERE referrer_id IS NOT NULL을 서브쿼리에 넣어도 같은 결과가 나온다.

3. 바깥 행의 카테고리로 최고가를 구해 비교한다. =로 비교하므로 값이 같은 메뉴는 모두 나온다.

1
2
3
4

SELECT m.category_id, m.name, m.price
FROM menu m
WHERE m.price = (SELECT MAX(s.price) FROM menu s WHERE s.category_id = m.category_id)
ORDER BY m.category_id, m.menu_id;

4. FROM 절의 서브쿼리(파생 테이블)에 별칭이 없어서 ERROR 1248 (42000): Every derived table must have its own alias가 난다. 괄호 뒤에 별칭을 붙인다.

SELECT AVG(cnt) AS avg_cnt
FROM (SELECT member_id, COUNT(*) AS cnt FROM orders
      WHERE member_id IS NOT NULL GROUP BY member_id) AS t;
