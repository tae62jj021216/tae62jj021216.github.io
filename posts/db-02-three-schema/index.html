[DB] 02. 3단계 스키마와 데이터 독립성

같은 카페 DB라도 카운터 직원, 급여 담당자, DB를 운영하는 사람이 보는 모습은 다르다. DBMS는 이 차이를 외부·개념·내부의 3단계 스키마로 나눠 관리하고, 그 덕분에 한 단계를 바꿔도 다른 단계가 영향을 덜 받는 데이터 독립성을 얻는다. 이 글에서는 3단계 스키마의 구조와 두 가지 데이터 독립성을 정리한다.

예제는 00편의 cafedb를 쓴다. 뷰·인덱스를 만드는 예제는 cafedb를 복사한 연습 DB cafe_practice에서 실행한다. SQL 문법은 8편부터 다룬다. 여기서는 결과만 보면 된다. MySQL 8.4에서 실행한 결과다.

스키마란

스키마(Schema)는 데이터베이스의 구조와 제약조건을 정의한 것이다. 어떤 테이블이 있고, 각 테이블에 어떤 열이 어떤 타입으로 있으며, 어떤 값이 허용되는지를 적은 설계도다. 스키마는 데이터에 대한 데이터, 즉 메타데이터이며 DBMS는 이것을 데이터 사전(시스템 카탈로그)에 저장한다.

MySQL에서는 information_schema(예: information_schema.columns)에서 스키마 정보를 조회할 수 있다. 스키마와 대비되는 인스턴스(어느 시점에 실제로 들어 있는 데이터)는 3편에서 다룬다.

3단계 스키마 구조

DBMS는 데이터베이스를 바라보는 관점을 세 단계로 나눈다. 표준화 단체(ANSI/SPARC)가 제안한 구조라서 ANSI/SPARC 3단계 구조라고도 한다.

개념 스키마는 데이터가 무엇이고 서로 어떻게 연결되는지만 말한다. 디스크의 어느 파일에 어떤 순서로 저장되는지는 말하지 않는다. DB 전체에 하나뿐이고, 보통 DBA가 설계하고 관리한다.

내부 스키마: 실제로 어떻게 저장하는가

내부 스키마는 개념 스키마의 테이블을 저장 장치에 어떻게 둘지 정한다. 레코드의 저장 형식, 어떤 열에 인덱스를 두는지, 어떤 저장 엔진을 쓰는지가 여기에 속한다. cafedb의 member와 orders에 걸린 인덱스를 조회해 보면 이렇다.

MySQL(InnoDB)은 기본키에는 항상 인덱스를 만들고, 외래키 열에는 쓸 수 있는 인덱스가 없을 때만 B-트리 인덱스를 자동으로 만든다. 위의 referrer_id, member_id 인덱스가 그렇게 생긴 것이다. DB를 쓰는 사람 대부분은 이런 저장 구조를 신경 쓰지 않는다.

외부 스키마: 사용자마다 필요한 부분만

외부 스키마는 사용자나 응용 프로그램 하나가 보는 DB의 모습으로, 개념 스키마에서 필요한 부분만 잘라 내거나 가공한 것이다. 카운터 직원은 회원의 이름·등급·전화번호만, 급여 담당자는 직원의 급여 정보만 필요하다(회원 정보는 보면 안 된다).

관계형 DBMS에서는 외부 스키마를 주로 뷰(VIEW)로 만든다. 뷰는 SELECT 결과에 이름을 붙인 가상 테이블이다(문법과 활용은 20편에서 자세히 다룬다).

USE cafe_practice;

CREATE VIEW counter_member AS
SELECT member_id, name, grade, phone FROM member;

CREATE VIEW payroll_staff AS
SELECT name, role, store, salary FROM staff;

두 뷰는 같은 개념 스키마 위에 만든 서로 다른 외부 스키마다. 외부 스키마가 여러 개일 수 있고, 여러 사용자가 같은 외부 스키마를 함께 쓸 수도 있다. 필요한 열만 보여 주므로 보안에도 도움이 된다.

주의할 점: 개수를 묻는 문제가 자주 나온다. 외부 스키마는 사용자·응용마다 여러 개, 개념 스키마와 내부 스키마는 DB 하나에 하나씩이다.

사상(Mapping)

단계 사이에는 한 단계의 모습을 다른 단계의 모습으로 바꿔 주는 사상(mapping)이 있다.

사상연결하는 단계cafedb 예
외부/개념 사상 (논리적 사상)외부 스키마 ↔ 개념 스키마counter_member의 phone은 member.phone이다 (뷰 정의)
개념/내부 사상 (물리적 사상)개념 스키마 ↔ 내부 스키마member 테이블은 InnoDB 파일에 기본키 순서로 저장되고, referrer_id에는 B-트리 인덱스가 있다

한 단계가 바뀌면 DBMS(또는 DBA)는 사상만 고쳐서 위 단계가 바뀐 사실을 모르게 한다. 이것이 데이터 독립성이다.

데이터 독립성

데이터 독립성은 하위 단계의 스키마를 바꿔도 상위 단계의 스키마와 응용 프로그램을 고치지 않아도 되는 성질이다. 파일 구조가 바뀌면 프로그램을 모두 고쳐야 했던 파일 시스템의 문제를 3단계 구조가 해결한다.

구분무엇이 바뀌어도무엇이 그대로인가지켜 주는 사상
논리적 데이터 독립성개념 스키마 (테이블 분리·추가, 열 추가 등)외부 스키마, 응용 프로그램외부/개념 사상
물리적 데이터 독립성내부 스키마 (인덱스 추가, 저장 방식 변경 등)개념 스키마 (그리고 외부 스키마, 응용 프로그램)개념/내부 사상

논리적 데이터 독립성: 테이블을 나눠도 뷰는 그대로

개인정보를 따로 관리하려고 member의 phone을 새 테이블로 옮긴다고 하자. 개념 스키마가 바뀌는 변경이라, 그대로 두면 member.phone을 가리키던 counter_member 뷰가 깨진다. 이때 고칠 곳은 카운터 프로그램이 아니라 뷰 정의(외부/개념 사상)다. 두 테이블을 합쳐 예전과 같은 열을 내놓도록 뷰만 다시 정의하면, 카운터 프로그램은 한 글자도 바꾸지 않고 같은 결과를 얻는다. 이것이 논리적 데이터 독립성이다. 뷰가 깨지는 모습과 고치는 SQL은 20편에서 직접 확인한다.

물리적 데이터 독립성: 인덱스를 추가해도 쿼리는 그대로

지점별 주문 조회가 잦아져서 orders.store에 인덱스를 추가한다고 하자. 테이블과 열은 그대로이고 저장 구조만 바뀌므로 내부 스키마의 변경이다. 같은 쿼리의 실행 계획(EXPLAIN)을 인덱스 추가 전후로 비교한다(인덱스는 9편에서 다룬다). 표에는 실행 계획의 일부 열만 옮겼다.

EXPLAIN SELECT order_id, member_id, ordered_at FROM orders WHERE store = '강변점' ORDER BY order_id;

EXPLAIN을 떼고 실행하면 두 번 모두 강변점 주문 4행(주문 번호 3, 4, 9, 12)이 똑같이 나온다. 달라진 것은 찾아가는 방법뿐이다. 추가 전에는 12행을 모두 훑었고, 추가 후에는 인덱스로 4행만 찾아갔다. 내부 스키마가 바뀌었지만 테이블 구조와 쿼리는 그대로다. 이것이 물리적 데이터 독립성이다.

주의할 점: 물리적 독립성은 DBMS가 알아서 지켜 주는 경우가 많지만, 논리적 독립성은 완전히 지키기 어렵다. 위 예처럼 뷰를 다시 정의해야 하고, 열을 아예 없애는 변경이라면 그 열을 쓰던 외부 스키마는 어쩔 수 없이 영향을 받는다.

복습 문제

  1. 다음 설명이 가리키는 스키마를 외부·개념·내부 중에서 고르시오. (가) 인덱스를 어느 열에 둘지, 레코드를 어떤 형식으로 저장할지 정한다. (나) 조직 전체의 테이블, 관계, 무결성 제약조건, 보안 규칙을 정의한다. (다) 서브스키마라고도 하며, 하나의 DB에 여러 개 존재할 수 있다.
  2. 다음 변경 중 논리적 데이터 독립성과 관련된 것을 모두 고르시오.
    • ① orders.ordered_at에 인덱스를 추가한다.
    • ② member 테이블에 birthday 열을 추가한다.
    • ③ 저장 엔진이나 데이터 파일의 위치를 바꾼다.
    • ④ staff 테이블을 staff와 staff_salary로 나눈다.
  3. 본문의 payroll_staff 뷰를 쓰는 급여 프로그램이 있다. staff.salary를 새 테이블 staff_salary(staff_id, salary)로 옮기고 staff에서 salary 열을 지웠다. 급여 프로그램을 고치지 않으려면 무엇을 어떻게 바꿔야 하는지 쓰고, 이것이 어떤 데이터 독립성인지 쓰시오.
  4. 다음 문장의 참·거짓을 판단하고, 거짓이면 고치시오. “물리적 데이터 독립성은 개념 스키마가 바뀌어도 내부 스키마가 영향을 받지 않는 성질이다.”
정답과 해설
  1. (가) 내부 스키마, (나) 개념 스키마, (다) 외부 스키마.
  2. ②, ④. 열 추가와 테이블 분리는 개념 스키마의 변경이라, 이때 외부 스키마·응용 프로그램이 영향을 받지 않는 것이 논리적 독립성이다. ①과 ③은 저장 구조(내부 스키마)의 변경이라 물리적 독립성과 관련된다.
  3. 프로그램이 아니라 payroll_staff 뷰의 정의(외부/개념 사상)를 바꾼다. staff와 staff_salary를 staff_id로 합쳐 예전과 같은 열(name, role, store, salary)을 내놓도록 뷰를 다시 정의하면, 급여 프로그램은 예전과 같은 결과를 받는다. 개념 스키마가 바뀌어도 외부 스키마와 응용 프로그램이 그대로이므로 논리적 데이터 독립성이다.
  4. 거짓. 방향이 반대다. 물리적 데이터 독립성은 내부 스키마가 바뀌어도 개념 스키마(와 그 위의 외부 스키마, 응용 프로그램)가 영향을 받지 않는 성질이다. 개념 스키마가 바뀌어도 외부 스키마가 영향을 받지 않는 것은 논리적 데이터 독립성이다.
