[DB] 08. CREATE, 데이터 타입, 제약조건

테이블을 만드는 CREATE는 “어떤 값을 담을지(데이터 타입)”와 “어떤 값을 막을지(제약조건)”를 함께 정한다. MySQL의 주요 데이터 타입, 제약조건을 거는 두 가지 방법, 외래키의 참조 동작(ON DELETE/ON UPDATE)을 정리한다.

예제는 00편의 cafedb와 같은 카페를 가정하고, 연습 DB cafe_practice에 테이블을 처음부터 만든다. 본문 SQL을 차례로 실행하면 글과 같은 결과가 나온다(MySQL 8.4).

실습 준비 SQL

이전 편에서 만든 연습 DB가 있으면 지운다. CREATE DATABASE부터는 본문에서 직접 실행한다.

1

DROP DATABASE IF EXISTS cafe_practice;

CREATE DATABASE

1
2

CREATE DATABASE cafe_practice DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE cafe_practice;
  • 문자 집합은 글자를 저장하는 방식, 콜레이션은 문자열을 비교·정렬하는 규칙이다.
  • MySQL의 utf8은 최대 3바이트인 utf8mb3의 별칭이라 이모지를 못 담는다. utf8mb4를 쓴다.
  • MySQL에서 CREATE SCHEMA는 CREATE DATABASE와 같다.

DOUBLE은 0.1을 2진수로 정확히 표현하지 못해 = 0.3 비교가 거짓(0)이 된다. 금액처럼 정확해야 하는 값은 DECIMAL로 저장한다.

DATETIME과 TIMESTAMP

둘 다 YYYY-MM-DD hh:mm:ss 형식이다. DATETIME은 넣은 값을 그대로 저장하고, TIMESTAMP는 UTC로 바꿔 저장했다가 읽을 때 세션 시간대로 되돌린다(범위도 1970~2038년으로 좁다). 그래서 +09:00에서 넣은 09:00:00을 +00:00 세션에서 읽으면 TIMESTAMP만 00:00:00으로 보인다.

CREATE TABLE과 제약조건

제약조건(constraint)은 규칙에 어긋나는 값이 들어오지 못하게 DBMS가 막는 장치다. 3편에서 본 무결성 제약조건을 실제 SQL로 거는 방법이다.

제약조건막는 것비고
NOT NULLNULL열 수준으로만 쓴다
UNIQUE중복 값NULL은 여러 개 들어갈 수 있다
PRIMARY KEY중복 값과 NULL테이블에 하나. UNIQUE + NOT NULL
FOREIGN KEY부모 테이블에 없는 값참조 무결성
CHECK조건식이 거짓인 값MySQL 8.0.16부터 검사한다
DEFAULT(막지 않음) 생략한 값의 기본값열 수준으로만 쓴다
AUTO_INCREMENT(막지 않음) 자동 번호MySQL 전용

열 수준으로 걸기

열 정의 바로 뒤에 제약조건을 붙인다. 짧고 읽기 쉽다.

1
2
3
4
5
6

CREATE TABLE menu (
    menu_id     INT          PRIMARY KEY,
    name        VARCHAR(30)  NOT NULL UNIQUE,
    price       INT          NOT NULL CHECK (price > 0),
    is_seasonal BOOLEAN      NOT NULL DEFAULT FALSE
);

DESCRIBE menu;로 열의 타입, NULL 허용 여부, 키(PRI 기본키, UNI 유니크), 기본값을 확인한다. 기본키 열은 NOT NULL을 쓰지 않아도 NULL을 막는다.

테이블 수준으로 걸기

열을 모두 쓴 뒤 CONSTRAINT 이름과 함께 따로 적는다. 이름을 붙여 두면 오류 메시지에 그 이름이 나오고, 9편에서 볼 ALTER TABLE ... DROP CONSTRAINT로 지우기도 쉽다.

CREATE TABLE menu2 (
    menu_id     INT,
    name        VARCHAR(30)  NOT NULL,
    price       INT          NOT NULL,
    is_seasonal BOOLEAN      NOT NULL DEFAULT FALSE,
    CONSTRAINT pk_menu2       PRIMARY KEY (menu_id),
    CONSTRAINT uq_menu2_name  UNIQUE (name),
    CONSTRAINT ck_menu2_price CHECK (price > 0)
);

주의할 점: MySQL은 기본키 제약조건의 이름을 무시하고 항상 PRIMARY로 둔다. 또 NOT NULL과 DEFAULT는 테이블 수준으로 쓸 수 없고, 여러 열을 묶는 복합 기본키·복합 유니크는 테이블 수준으로만 쓸 수 있다.

이름을 붙이지 않은 CHECK는 menu_chk_1처럼 자동 이름이 붙는다. menu2였다면 ck_menu2_price가 나와 무엇을 어겼는지 더 잘 보인다.

외래키와 참조 동작

외래키가 있으면 부모 테이블의 행을 지우거나 기본키 값을 바꿀 때 자식 행을 어떻게 할지 정해야 한다.

1
2

FOREIGN KEY (열) REFERENCES 부모테이블(열)
    [ON DELETE 동작] [ON UPDATE 동작]
동작부모 행을 지우거나 키를 바꾸면
CASCADE자식 행도 함께 지우거나 같은 값으로 바꾼다
SET NULL자식의 외래키 값을 NULL로 바꾼다
RESTRICT자식 행이 있으면 거부한다
NO ACTIONMySQL에서는 RESTRICT와 같다. 동작을 생략하면 이것이 기본값이다
SET DEFAULT자식의 외래키를 기본값으로 바꾼다(표준). MySQL 문서는 InnoDB가 지원하지 않는다고 적는다. 8.4에서 해 보면 테이블은 만들어지지만 부모 행 삭제가 ERROR 1451로 거부된다

지점(store) 하나를 부모로 두고, 동작이 다른 자식 테이블 세 개를 만든다. 근무표 shift는 지점·날짜·시간대 세 열을 합쳐야 행이 정해지므로 복합 기본키를 테이블 수준에서 묶는다.

CREATE TABLE store (
    store_id INT          AUTO_INCREMENT PRIMARY KEY,
    name     VARCHAR(20)  NOT NULL UNIQUE
);
CREATE TABLE staff (
    staff_id INT          PRIMARY KEY,
    name     VARCHAR(10)  NOT NULL,
    store_id INT          NULL,
    CONSTRAINT fk_staff_store FOREIGN KEY (store_id) REFERENCES store(store_id)
        ON DELETE SET NULL ON UPDATE CASCADE
);
CREATE TABLE shift (
    store_id  INT,
    work_date DATE,
    slot      CHAR(2),
    staff_cnt TINYINT      NOT NULL DEFAULT 1,
    CONSTRAINT pk_shift PRIMARY KEY (store_id, work_date, slot),
    CONSTRAINT fk_shift_store FOREIGN KEY (store_id) REFERENCES store(store_id)
        ON DELETE CASCADE ON UPDATE CASCADE
);
CREATE TABLE sales (
    sale_id  INT          AUTO_INCREMENT PRIMARY KEY,
    store_id INT          NOT NULL,
    amount   INT          NOT NULL,
    CONSTRAINT fk_sales_store FOREIGN KEY (store_id) REFERENCES store(store_id)
        ON DELETE RESTRICT ON UPDATE CASCADE
);

복합 기본키는 세 열 각각은 중복돼도 되고 세 값의 조합이 겹치면 막힌다. 부모에 없는 값(예: sales에 지점 9)을 자식에 넣으면 ERROR 1452로 막힌다.

공원점에는 직원 2명과 근무 2건이 있고 매출은 없다. 세 자식 테이블이 어떻게 될지 먼저 예측해 보자.

SELECT * FROM staff;

  • staff(SET NULL): 직원 행은 남고 store_id만 NULL이 됐다.
  • shift(CASCADE): 공원점의 근무 2건이 함께 지워졌다.
  • sales(RESTRICT): 공원점 매출이 없어 막지 않았다.

본점(1)은 매출이 있어서 RESTRICT에 걸리고, 문장이 통째로 실패하므로 staff, shift도 바뀌지 않는다.

1
2

DELETE FROM store WHERE store_id = 1;
-- ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`cafe_practice`.`sales`, CONSTRAINT `fk_sales_store` ...)

ON UPDATE CASCADE: 부모 키를 바꾸면

세 자식 모두 ON UPDATE CASCADE라서, 부모 키를 바꾸면 자식의 값도 따라 바뀐다.

1
2

UPDATE store SET store_id = 20 WHERE store_id = 2;
-- sales의 98000원 매출, staff의 향단, shift의 강변점 근무도 store_id가 20이 된다

sales는 삭제는 막지만(ON DELETE RESTRICT) 번호 변경은 따라가도록 따로 정한 것이다.

주의할 점: SET NULL은 외래키 열이 NULL을 허용해야 쓸 수 있다. NOT NULL 열에 걸면 테이블 생성부터 실패한다(ERROR 1830).

주의할 점: 표준 SQL에서 RESTRICT는 즉시, NO ACTION은 문장이 끝날 때 검사하지만 MySQL은 둘 다 즉시 검사한다. Oracle에는 ON UPDATE 절이 없다.

    member_id  INT          NOT NULL,
