[DB] 07. 정규화 ② 1NF부터 BCNF까지

6편의 주문표를 1NF → 2NF → 3NF 순서로 분해하고, 3NF로도 남는 문제를 BCNF로 정리한다. 4NF·5NF와 반정규화도 짧게 본다.

예제는 00편의 cafedb를 쓴다. 실습은 아래 “실습 준비 SQL”로 만드는 연습 DB cafe_practice에서 한다(MySQL 8.4). SQL 문법은 8편부터 다룬다. 여기서는 결과만 보면 된다.

실습 준비 SQL

6편의 order_sheet와 같은 order_1nf를 만들고, 주문별로 묶어 order_raw를 만든다(GROUP_CONCAT은 13편).

DROP DATABASE IF EXISTS cafe_practice;
CREATE DATABASE cafe_practice;
USE cafe_practice;

CREATE TABLE order_1nf (PRIMARY KEY (order_id, menu_id)) AS
SELECT o.order_id, o.store, mb.member_id, mb.name AS member_name, mb.grade,
       m.menu_id, m.name AS menu_name, m.price, oi.qty
FROM cafedb.orders o
JOIN cafedb.member mb     ON mb.member_id = o.member_id
JOIN cafedb.order_item oi ON oi.order_id = o.order_id
JOIN cafedb.menu m        ON m.menu_id = oi.menu_id;

CREATE TABLE order_raw (PRIMARY KEY (order_id)) AS
SELECT order_id, store, member_id, member_name, grade,
       GROUP_CONCAT(menu_id   ORDER BY menu_id SEPARATOR ', ') AS menu_ids,
       GROUP_CONCAT(menu_name ORDER BY menu_id SEPARATOR ', ') AS menu_names,
       GROUP_CONCAT(price     ORDER BY menu_id SEPARATOR ', ') AS prices,
       GROUP_CONCAT(qty       ORDER BY menu_id SEPARATOR ', ') AS qtys
FROM order_1nf GROUP BY order_id, store, member_id, member_name, grade;

정규화와 정규형

정규화(normalization)는 함수 종속을 기준으로 테이블을 분해해 중복과 이상 현상을 없애는 과정이다. 각 단계의 조건을 정규형(normal form)이라고 하며, 뒤 단계는 앞 단계의 조건을 모두 만족해야 한다.

정규형조건없애는 것
1NF모든 속성 값이 원자값한 칸의 여러 값, 반복 그룹
2NF1NF + 부분 함수 종속 없음기본키 일부에 대한 종속
3NF2NF + 이행 함수 종속 없음키가 아닌 속성을 거친 종속
BCNF모든 결정자가 후보키후보키가 아닌 결정자
4NFBCNF + 다치 종속 없음서로 독립인 다중값의 조합
5NF4NF + 조인 종속 없음후보키를 통하지 않는 조인 종속

주의할 점: 시험에서는 순서를 “도부이결다조”(도메인 원자값 → 부분 종속 → 이행 종속 → 결정자 → 다치 종속 → 조인 종속)로 외운다.

출발점: 메뉴를 쉼표로 적은 주문표

6편의 order_sheet보다 더 거친 표에서 시작한다. 주문 한 건을 한 행에 적고, 메뉴 번호·이름·가격·수량을 쉼표로 이어 적은 order_raw(10행, 기본키 order_id)다. 지점·회원 번호·등급 열은 생략했다.

1NF: 한 칸에는 값 하나

제1정규형(1NF)은 모든 속성의 도메인이 원자값(atomic value)만 갖는 것이다. menu1, menu2처럼 같은 종류의 열을 번호만 바꿔 늘어놓는 반복 그룹도 1NF 위반이다. order_raw는 menu_names 한 칸에 메뉴가 여러 개라 1NF가 아니다. 이 구조에서는 검색부터 틀린다.

1
2

SELECT order_id, menu_names FROM order_raw
WHERE menu_names LIKE '%콜드브루%' ORDER BY order_id;
order_idmenu_names
4콜드브루, 초코케이크
8아메리카노, 콜드브루 라떼
12콜드브루 라떼

콜드브루를 산 주문은 4번뿐인데 ‘콜드브루 라떼’까지 걸렸다. 메뉴별 수량 합계도 SUM으로 구할 수 없다.

쉼표 목록을 풀어 메뉴 하나당 한 행으로 펴면 1NF가 된다. 이것이 기본키 (order_id, menu_id)인 order_1nf(16행)이며 6편의 order_sheet와 같다. 이제 menu_name = '콜드브루'로 정확히 찾을 수 있지만, 부분 종속과 이행 종속 때문에 6편의 이상 현상은 그대로 남는다.

2NF: 부분 함수 종속 없애기

제2정규형(2NF)은 1NF이면서, 기본키가 아닌 모든 속성이 기본키에 완전 함수 종속인 것이다. 6편에서 찾은 부분 종속은 두 개였다.

  • order_id → store, member_id, member_name, grade (기본키의 일부 order_id에 종속)
  • menu_id → menu_name, price (기본키의 일부 menu_id에 종속)

기본키의 부분마다 테이블을 만들어 종속된 속성을 옮기고, 키 전체에 종속된 qty만 원래 키와 남긴다. 아래 SQL은 고른 열로 새 테이블을 만들고 괄호 안의 기본키를 붙인다.

1
2
3
4

CREATE TABLE orders_2nf (PRIMARY KEY (order_id)) AS
  SELECT DISTINCT order_id, store, member_id, member_name, grade FROM order_1nf;
CREATE TABLE menu_2nf (PRIMARY KEY (menu_id)) AS
  SELECT DISTINCT menu_id, menu_name, price FROM order_1nf;
CREATE TABLE item_2nf (PRIMARY KEY (order_id, menu_id)) AS
  SELECT order_id, menu_id, qty FROM order_1nf;

orders_2nf 10행, menu_2nf 11행, item_2nf 16행이 됐다. 공통 속성이 각 테이블의 기본키라서 무손실 분해다(6편의 조건). 메뉴 정보가 한 번만 저장되므로 안 팔린 새 메뉴도 넣을 수 있다.

1
2

INSERT INTO menu_2nf VALUES (12, '흑임자라떼', 5800);
-- Query OK, 1 row affected

그러나 orders_2nf에는 홍길동의 등급이 주문 1·5·11번에 반복되고, 주문 없는 회원은 넣을 수 없다.

1

INSERT INTO orders_2nf VALUES (NULL, NULL, 108, '팥쥐', 'BASIC');
-- ERROR 1048 (23000): Column 'order_id' cannot be null

3NF: 이행 함수 종속 없애기

제3정규형(3NF)은 2NF이면서, 기본키가 아닌 속성이 기본키에 이행 종속되지 않는 것이다. orders_2nf에는 order_id → member_id → member_name, grade가 있다. 중간 다리인 member_id를 기본키로 하는 테이블을 따로 만들어 회원 정보를 옮긴다.

CREATE TABLE member (PRIMARY KEY (member_id)) AS
  SELECT DISTINCT member_id, member_name, grade FROM orders_2nf;
CREATE TABLE menu (PRIMARY KEY (menu_id)) AS SELECT * FROM menu_2nf;
CREATE TABLE orders (PRIMARY KEY (order_id)) AS
  SELECT order_id, store, member_id FROM orders_2nf;
CREATE TABLE order_item (PRIMARY KEY (order_id, menu_id)) AS SELECT * FROM item_2nf;

-- 외래키는 따로 붙인다(AS SELECT에는 쓸 수 없다)
ALTER TABLE orders     ADD FOREIGN KEY (member_id) REFERENCES member(member_id);
ALTER TABLE order_item ADD FOREIGN KEY (order_id) REFERENCES orders(order_id),
                       ADD FOREIGN KEY (menu_id)  REFERENCES menu(menu_id);

회원 7행, 메뉴 12행(흑임자라떼 포함), 주문 10행, 주문 상세 16행이 됐다. 6편의 세 이상이 사라졌는지 확인한다.

DELETE FROM order_item WHERE order_id = 10;
DELETE FROM orders WHERE order_id = 10;

이 3NF 결과는 cafedb와 같은 모양(4개 테이블)이다. cafedb는 처음부터 3NF로 설계됐고, 비회원 주문(member_id가 NULL)을 허용하며 열이 몇 개 더 있다.

주의할 점: 이행 종속을 끊을 때 중간 다리 속성(member_id)은 원래 테이블에 남겨 외래키로 쓴다. 이것까지 옮기면 주문과 회원을 다시 연결할 수 없다.

BCNF: 모든 결정자가 후보키

3NF는 “기본키가 아닌 속성”만 검사하므로 키에 속한 속성끼리의 종속은 놓친다. BCNF(Boyce-Codd 정규형)는 이 빈틈까지 막는다.

자명하지 않은 모든 함수 종속 X → Y에서 X는 슈퍼키여야 한다. 시험에서는 “결정자가 모두 후보키”로 표현한다.

주문표는 3NF에서 이미 BCNF이므로(모든 결정자가 기본키) 바리스타 교실 예를 따로 만든다.

  • 강사 한 명은 한 과목만 가르친다: trainer → course
  • 회원은 한 과목을 강사 한 명에게만 배운다: (member_id, course) → trainer

INSERT INTO class_enroll VALUES
 (101, '라떼아트', '장화'),
 (101, '핸드드립', '전우치'),
 (102, '라떼아트', '홍련'),
 (103, '라떼아트', '장화'),
 (104, '핸드드립', '전우치');

후보키는 (member_id, course)와 (member_id, trainer)다. 모든 속성이 후보키에 속해 3NF는 만족하지만, 결정자 trainer가 후보키가 아니므로 BCNF가 아니다. 강사-과목 사실이 수강생 수만큼 반복되고, 수강생 없는 강사는 등록할 수 없다.

1
2

INSERT INTO class_enroll (course, trainer) VALUES ('핸드드립', '방자');
-- ERROR 1364 (HY000): Field 'member_id' doesn't have a default value

결정자 trainer를 기본키로 하는 테이블을 떼어 낸다.

CREATE TABLE trainer_course (PRIMARY KEY (trainer)) AS

ALTER TABLE trainer_enroll ADD FOREIGN KEY (trainer) REFERENCES trainer_course(trainer);

조인하면 원래 5행이 그대로 나온다(무손실). 그런데 (member_id, course) → trainer는 이제 어느 테이블에서도 검사되지 않는다.

1

INSERT INTO trainer_enroll VALUES (101, '홍련');   -- 101은 이미 라떼아트를 장화에게 배운다
-- Query OK, 1 row affected

홍길동이 라떼아트 강사 두 명에게 등록됐다. BCNF 분해는 이렇게 종속성 보존을 포기해야 할 때가 있다. 3NF까지는 무손실과 종속성 보존을 함께 지키는 분해가 항상 가능하므로, 실무에서는 3NF에서 멈추기도 한다.

주의할 점: BCNF이면 항상 3NF지만 반대는 아니다. 둘은 이 예처럼 후보키가 여러 개이고 서로 겹칠 때 갈린다.

4NF와 5NF

  • 4NF: 다치 종속을 없앤다. 서로 무관한 사이즈와 온도를 (menu_id, size, temp) 한 테이블에 두면 모든 조합을 채워야 하므로, (menu_id, size)와 (menu_id, temp)로 나눈다.
  • 5NF: 셋 이상으로 나눠야만 무손실이 되는 조인 종속을 없앤다.

반정규화

정규화할수록 조인이 늘어나므로 조회 성능이 중요한 곳에서는 일부러 중복을 허용하기도 한다. 이것을 반정규화(denormalization)라고 한다.

방법예치르는 값
계산 값 저장orders에 주문 합계 열 추가수량·가격이 바뀔 때마다 합계도 고쳐야 한다
열 중복orders에 회원 이름 복사회원 이름이 바뀌면 갱신 이상
테이블 병합·분할오래된 주문을 따로 분리구조가 복잡해진다

반정규화는 정규화를 먼저 끝낸 뒤 성능 문제가 확인된 곳에만 적용한다. 처음부터 정규화하지 않은 것과는 다르다.

주의할 점: 주문 당시의 가격(unit_price)을 주문 상세에 두는 것은 반정규화가 아니다. 현재 가격과 다른 사실이고 (order_id, menu_id)에 완전 종속이다.

복습 문제

  1. R(메뉴번호, 메뉴명, 공급처코드, 공급처명)의 기본키는 메뉴번호이고, 공급처코드 → 공급처명이다. R이 2NF는 만족하지만 3NF는 아닌 이유를 쓰고 분해하시오.
  2. 다음 설명 중 옳은 것을 모두 고르시오.
    • ① BCNF를 만족하는 테이블은 3NF를 만족한다.
    • ② 후보키가 속성 하나로 된 기본키 하나뿐인 1NF 테이블은 항상 2NF다.
    • ③ 3NF 분해는 항상 종속성을 보존할 수 있지만, BCNF 분해는 그렇지 않을 수 있다.
    • ④ 반정규화는 정규화를 하지 않은 설계를 말한다.
  3. 운동 센터의 R(회원, 종목, 코치)에서 (회원, 종목) → 코치, 코치 → 종목이다. 후보키를 모두 쓰고, R이 3NF인지 BCNF인지 판단하시오.
정답과 해설
  1. 기본키가 메뉴번호 하나라서 부분 종속은 없으므로 2NF다. 그러나 메뉴번호 → 공급처코드 → 공급처명의 이행 종속이 있어 3NF가 아니다. 메뉴(메뉴번호, 메뉴명, 공급처코드), 공급처(공급처코드, 공급처명)로 나눈다(공급처코드는 외래키로 남긴다).
  2. ①, ②, ③. ②는 후보키가 하나뿐이라는 조건이 있어 참이다(다른 복합 후보키가 있으면 부분 종속이 생길 수 있다). ④는 틀렸다. 반정규화는 정규화를 끝낸 뒤 성능을 위해 일부러 중복을 들이는 것이다.
  3. 후보키는 (회원, 종목)과 (회원, 코치)다. 모든 속성이 후보키에 속하므로 후보키에 속하지 않는 속성이 없어 3NF다. 그러나 결정자 코치가 후보키가 아니므로 BCNF는 아니다. BCNF로 나누면 (코치, 종목), (회원, 코치)가 된다.
