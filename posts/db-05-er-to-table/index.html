4편에서 cafedb를 개체와 관계로 정리했다. 이 글에서는 그 ER 모델을 관계형 테이블로 바꾸는 매핑 규칙(논리적 설계)을 정리하고, 규칙대로 만든 테이블에서 제약이 어떻게 동작하는지 확인한다.

예제는 00편의 cafedb를 쓴다. 제약이 동작하는 모습은 아래 “실습 준비 SQL”로 만든 연습 DB cafe_practice에서 확인한다(MySQL 8.4). SQL 문법은 8편부터 다룬다. 여기서는 결과만 보면 된다.

DROP DATABASE IF EXISTS cafe_practice;
CREATE DATABASE cafe_practice;
USE cafe_practice;

CREATE TABLE member (
    member_id INT PRIMARY KEY, name VARCHAR(10) NOT NULL,
    grade VARCHAR(10) NOT NULL DEFAULT 'BASIC', city VARCHAR(10), joined_on DATE NOT NULL
);
CREATE TABLE category (
    category_id INT PRIMARY KEY, name VARCHAR(20) NOT NULL, parent_id INT NULL,
    FOREIGN KEY (parent_id) REFERENCES category(category_id)
);
CREATE TABLE orders (
    order_id INT PRIMARY KEY, member_id INT NULL,
    store VARCHAR(10) NOT NULL, ordered_at DATETIME NOT NULL,
    FOREIGN KEY (member_id) REFERENCES member(member_id)
);
CREATE TABLE menu (
    menu_id INT PRIMARY KEY, name VARCHAR(30) NOT NULL,
    category_id INT NOT NULL, price INT NOT NULL,
    FOREIGN KEY (category_id) REFERENCES category(category_id)
);
CREATE TABLE order_item (
    order_id INT, menu_id INT, qty INT NOT NULL,
    PRIMARY KEY (order_id, menu_id),
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (menu_id)  REFERENCES menu(menu_id)
);
CREATE TABLE staff (
    staff_id INT PRIMARY KEY, name VARCHAR(10) NOT NULL, role VARCHAR(10) NOT NULL,
    manager_id INT NULL,
    FOREIGN KEY (manager_id) REFERENCES staff(staff_id)
);

INSERT INTO member     SELECT member_id, name, grade, city, joined_on FROM cafedb.member;
INSERT INTO category   SELECT * FROM cafedb.category ORDER BY category_id;
INSERT INTO orders     SELECT * FROM cafedb.orders;

INSERT INTO order_item SELECT * FROM cafedb.order_item;
INSERT INTO staff      SELECT staff_id, name, role, manager_id FROM cafedb.staff ORDER BY staff_id;

본문에서는 매핑 결과를 테이블(열, …)로 적는다. PK는 기본키, FK→X는 X를 참조하는 외래키다.

규칙 1. 개체는 테이블이 된다

강한 개체 하나가 테이블 하나가 된다. 속성은 열이 되고, 키 속성은 기본키가 된다.

1
2

member   (member_id PK, name, grade, city, joined_on)   -- 연락처는 규칙 7에서 따로 뺀다
category (category_id PK, name, parent_id FK→category)

단순·단일값 속성은 열 하나가 되고, 복합 속성은 쪼갠 하위 속성만 열로 둔다(주소 → city, district, address_detail). 다중값 속성은 규칙 7, 유도 속성은 규칙 4 끝에서 본다.

규칙 2. 1:N 관계는 N쪽에 외래키를 둔다

회원(1)과 주문(N)의 주문함 관계는 N쪽인 orders에 회원의 기본키를 외래키로 넣는다. 관계의 속성도 N쪽 테이블에 넣는다.

1

orders (order_id PK, member_id FK→member NULL 허용, store, ordered_at)

1쪽인 member에 두면 한 칸에 주문 번호 1, 5, 11이 함께 들어가야 한다. 한 칸에는 값 하나만 들어가므로(1NF, 7편) 외래키는 N쪽에 둔다.

규칙 3. 전체 참여는 NOT NULL로 표현한다

N쪽 개체가 관계에 전체 참여하면 외래키 열에 NOT NULL을 붙이고, 부분 참여면 NULL을 허용한다(orders.member_id, 비회원 주문). 모든 메뉴는 반드시 카테고리 하나에 속하므로 menu.category_id는 NOT NULL이다.

1

menu (menu_id PK, name, category_id FK→category NOT NULL, price)

INSERT INTO menu VALUES (12, '흑임자라떼', NULL, 5800);
-- ERROR 1048 (23000): Column 'category_id' cannot be null

주의할 점: NOT NULL로 강제할 수 있는 것은 외래키를 가진 쪽(N쪽)의 전체 참여뿐이다. “모든 카테고리에는 메뉴가 최소 하나 있어야 한다”처럼 1쪽의 전체 참여는 테이블 정의만으로 막을 수 없어서 트리거나 응용 프로그램에서 확인한다.

규칙 4. M:N 관계는 교차 테이블로 만든다

주문과 메뉴의 담기 관계는 M:N이다. 어느 한쪽에 외래키를 넣으면 한 칸에 여러 값이 들어가야 하므로, 관계 자체를 교차 테이블(연결 테이블, 주문 상세)로 만든다. 양쪽 개체의 기본키를 외래키로 가져와 복합 기본키로 묶고, 관계의 속성(qty)도 여기에 둔다.

1

order_item (order_id FK→orders, menu_id FK→menu, qty)   PK = (order_id, menu_id)

복합 기본키 덕분에 같은 주문에 같은 메뉴가 두 줄로 들어가지 않는다(수량은 기존 행의 qty를 고친다). 여러 줄로 따로 담아야 하는 업무라면 (order_id, line_no)처럼 줄 번호를 기본키에 쓴다.

1
2

INSERT INTO order_item VALUES (1, 1, 3);
-- ERROR 1062 (23000): Duplicate entry '1-1' for key 'order_item.PRIMARY'

교차 테이블을 가운데 두고 조인하면 원래의 M:N 관계를 다시 읽을 수 있다. 유도 속성인 주문 합계도 이렇게 필요할 때 계산한다(조인은 15편, 집계는 13편).

SELECT oi.order_id, SUM(m.price * oi.qty) AS total
FROM order_item oi JOIN menu m ON m.menu_id = oi.menu_id
WHERE oi.order_id = 1
GROUP BY oi.order_id;

합계를 열로 저장하면 조회는 빨라지지만 수량이나 가격을 고칠 때마다 합계도 고쳐야 한다(7편의 반정규화).

규칙 5. 1:1 관계는 한쪽에 외래키 + UNIQUE

지점-점장 1:1 관계를 만든다고 하자. 1:1도 한쪽에 외래키를 두고, 그 외래키에 UNIQUE를 붙여 “최대 1”을 보장한다. 외래키는 전체 참여하는 쪽에 두는 것이 좋다. 모든 지점에는 점장이 있지만 모든 직원이 점장은 아니므로 store 쪽에 둔다(선택 참여 쪽에 두면 NULL이 많아진다).

staff (staff_id PK, name, role, manager_id FK→staff)   -- 순환 관계, 규칙 8

CREATE TABLE store (
    store_name VARCHAR(10) PRIMARY KEY,
    phone      VARCHAR(13),
    manager_id INT NOT NULL UNIQUE,     -- 전체 참여 + 1:1
    FOREIGN KEY (manager_id) REFERENCES staff(staff_id)
);

INSERT INTO store VALUES ('본점', '02-100-0001', 2), ('강변점', '02-100-0002', 3);

INSERT INTO store VALUES ('공원점', '02-100-0003', 2);   -- 2번 직원은 이미 본점 점장
-- ERROR 1062 (23000): Duplicate entry '2' for key 'store.manager_id'

UNIQUE를 빼면 한 직원이 여러 지점의 점장이 될 수 있어 1:N이 된다. 1:1과 1:N은 테이블 모양이 같고 UNIQUE 하나로 갈린다. 양쪽이 모두 전체 참여하는 1:1이라면 두 개체를 테이블 하나로 합치는 방법도 있다.

규칙 6. 약한 개체는 복합 기본키 + ON DELETE CASCADE

4편의 약한 개체 메뉴 옵션은 메뉴 번호를 빌려야 식별되므로, 소유 개체의 기본키와 부분 키를 묶어 기본키로 삼는다. 소유 개체가 사라지면 약한 개체도 존재할 수 없으므로 부모 행을 지울 때 함께 지우는 ON DELETE CASCADE를 붙인다.

CREATE TABLE menu_option (
    menu_id     INT,
    option_name VARCHAR(20),                       -- 부분 키
    extra_price INT NOT NULL DEFAULT 0,
    PRIMARY KEY (menu_id, option_name),            -- 소유 개체 키 + 부분 키

주문에 담긴 메뉴 1번은 order_item의 외래키에 CASCADE가 없어 거부된다. 약한 개체는 소유 개체와 운명을 같이하지만, 판매 기록은 메뉴를 지운다고 사라지면 안 된다. 그래서 외래키마다 삭제 동작을 따로 정한다(종류는 8편).

규칙 7. 다중값 속성은 별도 테이블로

규칙 8. 순환 관계와 ISA

순환 관계는 같은 테이블 안에 자기 기본키를 참조하는 외래키를 둔다. staff.manager_id가 그것으로, 없는 직원 번호를 상사로 넣으면 ERROR 1452로 거부된다. 1:N 순환이면 이렇게 열 하나로 충분하고, M:N 순환(예: 메뉴끼리 “함께 추천”)이면 같은 테이블을 두 번 참조하는 교차 테이블을 만든다. 상사 이름을 함께 보는 셀프 조인은 17편에서 다룬다.

ISA 관계(직원 → 정규직/파트타임)는 세 가지 방법 중 하나로 바꾼다.

방법테이블장점단점
상위·하위 모두 테이블로staff, fulltime(staff_id, 월급), parttime(staff_id, 시급)중복 없음, 가장 일반적조회할 때 조인이 필요하다
하위 개체만 테이블로fulltime(staff_id, 이름, 월급), parttime(…)조인 없음공통 속성이 반복된다
테이블 하나로staff(staff_id, 이름, 구분, 월급, 시급)가장 단순하다해당 없는 열이 NULL이 된다

첫 번째 방법에서 하위 테이블의 기본키는 상위 테이블을 참조하는 외래키이기도 하다.

매핑 규칙 한눈에 보기

ER 요소테이블로 바꾸는 법
강한 개체 / 복합 속성 / 유도 속성테이블(키 → 기본키) / 하위 속성만 열로 / 저장하지 않고 계산
1:N 관계N쪽에 외래키 (관계 속성도 N쪽), N쪽 전체 참여면 NOT NULL
1:1 관계한쪽(전체 참여 쪽)에 외래키 + UNIQUE
M:N 관계교차 테이블, 두 외래키로 복합 기본키
약한 개체소유 키 + 부분 키로 복합 기본키, ON DELETE CASCADE
다중값 속성별도 테이블, (개체 키, 값) 복합 기본키
순환 관계자기 테이블을 참조하는 외래키

이렇게 만든 테이블도 속성을 잘못 묶으면 이상 현상이 생긴다. 다음 편부터 정규화로 이를 고친다.

복습 문제

  1. 강사(1)와 강좌(N) 사이의 “담당” 관계가 있다. 외래키는 어느 테이블에 두어야 하는지, 반대쪽에 두면 어떤 문제가 생기는지 쓰시오.
  2. 회원과 쿠폰 사이에 M:N “보유” 관계가 있고, 관계에 발급일 속성이 있다. member(member_id), coupon(coupon_id)가 이미 있을 때 보유 관계를 나타내는 테이블의 CREATE TABLE 문을 쓰시오.
  3. 다음 중 NOT NULL로 표현할 수 없는 참여 제약을 고르고 이유를 쓰시오.
    ① 모든 주문은 반드시 지점 하나에 속한다 ② 모든 지점에는 주문이 최소 한 건 있어야 한다
  4. 본문을 모두 실행한 cafe_practice에서 아래 두 문장을 차례로 실행하면 각각 어떻게 되는지 쓰시오.

정답과 해설

  1. N쪽인 강좌 테이블에 instructor_id 외래키를 둔다. 강사 쪽에 두면 한 칸에 강좌 번호 여러 개를 넣거나 열을 늘려야 한다.

  2. 두 개체의 기본키를 외래키로 가져와 복합 기본키로 묶고, 관계 속성을 열로 둔다.

  4. 첫 문장은 실패한다(ERROR 1451, orders_ibfk_1). 101번 회원을 참조하는 주문이 있고 orders.member_id 외래키에 CASCADE가 없기 때문이다(member_phone의 CASCADE는 소용없다). 두 번째 문장은 성공한다(1 row affected). 108번 회원은 주문도 연락처도 없다.
