여러 SQL을 “전부 반영하거나 전부 취소하는” 트랜잭션, 동시 실행의 문제와 해결 방법(잠금, 고립 수준), 장애 회복을 정리한다.

예제는 00편의 cafedb 회원 세 명으로 만든 포인트 테이블을 쓴다. 아래 “실습 준비 SQL”로 cafe_practice를 만든 뒤 본문 SQL을 순서대로 실행한다. MySQL 8.4(InnoDB) 기준이다.

트랜잭션과 ACID

성춘향이 이몽룡에게 3,000포인트를 선물하려고 적립 → 차감 순으로 실행한다.

1
2
3

UPDATE point_account SET point = point + 3000 WHERE member_id = 103;   -- 이몽룡 8000 (자동 커밋)
UPDATE point_account SET point = point - 3000 WHERE member_id = 102;
-- ERROR 3819 (HY000): Check constraint 'point_account_chk_1' is violated.

차감은 실패했는데 적립은 이미 확정돼 이몽룡이 8,000이 됐다. 트랜잭션은 여러 SQL을 하나로 묶은 논리적 작업 단위로, 모두 반영되거나(COMMIT) 하나도 반영되지 않아야(ROLLBACK) 한다.

성질뜻보장하는 쪽
원자성 (Atomicity)전부 실행되거나 전부 취소된다 (All or Nothing)회복 기법 (UNDO)
일관성 (Consistency)실행 전후로 DB가 제약조건을 만족한다무결성 제약조건
고립성·격리성 (Isolation)실행 중인 트랜잭션의 중간 결과를 남이 볼 수 없다동시성 제어 (잠금)
지속성 (Durability)커밋된 결과는 장애가 나도 사라지지 않는다회복 기법 (로그, REDO)

트랜잭션 제어문 (TCL)

명령하는 일
START TRANSACTION (또는 BEGIN)트랜잭션 시작. 이후 문장은 자동 커밋되지 않는다
COMMIT변경을 확정한다
ROLLBACK변경을 모두 취소한다
SAVEPOINT 이름되돌아갈 지점을 표시한다
ROLLBACK TO [SAVEPOINT] 이름그 지점 이후만 취소한다. 트랜잭션은 계속된다

SAVEPOINT: 일부만 되돌리기

홍길동이 버터쿠키(3,000) 결제 뒤 저장점을 만들고, 밤 마들렌(3,500)을 결제했다가 마들렌만 취소한다.

START TRANSACTION;
UPDATE point_account SET point = point - 3000 WHERE member_id = 101;
INSERT INTO point_log (member_id, amount, memo) VALUES (101, -3000, '버터쿠키 결제');
SAVEPOINT after_cookie;
UPDATE point_account SET point = point - 3500 WHERE member_id = 101;
INSERT INTO point_log (member_id, amount, memo) VALUES (101, -3500, '밤 마들렌 결제');
-- 101: point 1500, point_log 1·2번
ROLLBACK TO SAVEPOINT after_cookie;
-- 101: point 5000, point_log 1번(버터쿠키)만
COMMIT;

DDL은 트랜잭션을 자동으로 커밋한다

CREATE, ALTER, DROP, TRUNCATE 같은 DDL은 진행 중인 트랜잭션을 암묵적으로 커밋한다.

트랜잭션의 상태

정상 경로는 활동(Active) → 부분 완료(Partially Committed) → 완료(Committed)이고, 문제가 생기면 실패(Failed) → 철회(Aborted)로 가서 시작 전 상태로 돌아간다. 부분 완료는 마지막 연산을 마쳤지만 커밋 전이다.

동시에 실행하면 생기는 문제

여러 트랜잭션을 순서 제어 없이 번갈아 실행하면 다음 문제가 생긴다(R 읽기, W 쓰기, 이몽룡의 포인트 5,000).

갱신 손실 (Lost Update): T1은 3,000 결제, T2는 1,000 적립이다.

순서T1 (결제 −3000)T2 (적립 +1000)
1R(point) = 5000 
2 R(point) = 5000
3W(point) = 2000, COMMIT 
4 W(point) = 6000, COMMIT

결과는 3,000이 아니라 6,000으로, T1의 결제가 사라졌다.

문제스케줄 (T1, T2)핵심
오손 읽기 (Dirty Read)T1 W(6000, 커밋 전) → T2 R(6000) → T1 ROLLBACK취소된 값을 읽음
반복 불가능한 읽기 (Non-repeatable Read)T1 R(5000) → T2 W(6000), COMMIT → T1 R(6000)같은 행의 값이 바뀜 (UPDATE)
유령 읽기 (Phantom Read)T1 point >= 5000 2명 → T2 INSERT, COMMIT → T1 3명없던 행이 나타남 (INSERT/DELETE)

읽는 도중 값이 바뀌어 합계가 틀리는 모순성, 철회된 값을 읽은 트랜잭션까지 되돌리는 연쇄 복귀도 있다.

스케줄과 직렬 가능성

직렬 스케줄은 한 트랜잭션이 끝난 뒤 다음을 실행해 정확하지만 느리고, 비직렬 스케줄은 번갈아 실행해 빠르지만 위의 문제가 생길 수 있다. 번갈아 실행했지만 결과가 어떤 직렬 스케줄과 같은 것이 직렬 가능 스케줄이고, 동시성 제어는 이런 스케줄만 허용하는 것이 목표다. 갱신 손실(6,000)은 어느 직렬 순서(3,000)와도 달라 직렬 가능하지 않다.

잠금 (Locking)

잠금얻는 경우다른 트랜잭션의 S 요청다른 트랜잭션의 X 요청
공유 잠금 (Shared, S)읽을 때허용대기
배타 잠금 (Exclusive, X)쓸 때대기대기

InnoDB에서 UPDATE·DELETE는 대상 행에 X 잠금을 자동으로 걸고, SELECT ... FOR SHARE는 S, FOR UPDATE는 X 잠금을 건다. 결제·적립이 FOR UPDATE로 읽으면 뒤에 온 쪽이 기다려 갱신 손실이 막힌다. 잠금 단위가 크면 오버헤드가 작지만 병행성이 낮고, 작으면 그 반대다.

2단계 잠금 규약(2PL)은 잠금을 얻기만 하는 확장 단계와 풀기만 하는 축소 단계로 나눈다. 모두 2PL을 지키면 직렬 가능성이 보장되지만 교착상태는 막지 못한다. 실무에서는 X 잠금을 커밋·롤백까지 쥐는 엄격한(Strict) 2PL을 주로 쓴다.

교착상태 (Deadlock)

서로 상대가 쥔 잠금을 기다리며 멈춘 상태다.

두 세션 실습: 클라이언트 창(mysql 또는 Workbench 탭)을 두 개 열어 세션 A, B로 쓰고, 둘 다 USE cafe_practice;를 먼저 실행한 뒤 번호 순서대로 번갈아 실행한다. 잠금 대기는 기본 50초(innodb_lock_wait_timeout)가 지나면 ERROR 1205로 끝나니 그 안에 다음 번호를 실행한다.

작업 전 101은 5500, 102는 3000이다.

-- 세션 A
START TRANSACTION;
UPDATE point_account SET point = point - 1000 WHERE member_id = 101;  -- ① 101 X 잠금
UPDATE point_account SET point = point + 1000 WHERE member_id = 102;  -- ③ B를 기다림, ④ 뒤 완료
COMMIT;                                                               -- ⑤

1
2
3
4
5

-- 세션 B
START TRANSACTION;
UPDATE point_account SET point = point - 500 WHERE member_id = 102;   -- ② 102 X 잠금
UPDATE point_account SET point = point + 500 WHERE member_id = 101;   -- ④ A를 기다림 → 교착상태
-- ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

InnoDB는 대기 사이클을 즉시 탐지해 희생자 B의 트랜잭션 전체를 롤백했다. SELECT * FROM point_account ORDER BY member_id;로 보면 101은 4500, 102는 4000(A의 +1000만 반영), 103은 5000이다.

발생 조건은 상호 배제, 점유와 대기, 비선점, 환형 대기가 모두 성립하는 것이다. 해결 방법은 예방(예: 같은 순서로 잠금), 회피(예: wait-die·wound-wait, 교재에 따라 예방으로 분류), 탐지 후 회복이다.

고립 수준 (Isolation Level)

표준 SQL은 허용할 문제에 따라 네 고립 수준을 정한다. 엄격할수록 정확하지만 느리다.

고립 수준오손 읽기반복 불가능한 읽기유령 읽기
READ UNCOMMITTED발생발생발생
READ COMMITTED방지발생발생
REPEATABLE READ방지방지발생
SERIALIZABLE방지방지방지

MySQL(InnoDB)의 기본값은 REPEATABLE READ(SELECT @@transaction_isolation;으로 확인), Oracle과 SQL Server의 기본값은 READ COMMITTED다. SET SESSION TRANSACTION ISOLATION LEVEL ...은 이 세션만 바꾼다.

세션 A가 START TRANSACTION 전에 SET SESSION TRANSACTION ISOLATION LEVEL ...로 수준을 정하고, 트랜잭션 안에서 이몽룡의 포인트를 세 번 읽었다(SELECT point FROM point_account WHERE member_id = 103;). 세션 B는 ① 뒤에 START TRANSACTION과 1,000 적립 UPDATE를, ② 뒤에 COMMIT을 실행했다. 수준마다 시작 전에 UPDATE point_account SET point = 5000 WHERE member_id = 103;으로 되돌렸다.

세션 A의 고립 수준①②③해석
READ UNCOMMITTED500060006000오손 읽기
READ COMMITTED500050006000반복 불가능한 읽기
REPEATABLE READ500050005000같은 값을 본다
SERIALIZABLE500050005000B의 UPDATE가 A의 커밋까지 대기

주의할 점: InnoDB의 REPEATABLE READ는 스냅숏(MVCC)과 넥스트 키 잠금으로 유령 읽기도 대부분 막지만, 시험에서는 표준대로 “발생”으로 답한다.

장애와 회복 (Recovery)

DBMS는 장애에 대비해 로그에 변경의 이전 값·이후 값과 시작·커밋 기록을 남긴다. UNDO는 이전 값으로 미완료 트랜잭션을 취소하고(원자성), REDO는 이후 값으로 커밋된 변경을 살린다(지속성).

WAL(Write-Ahead Logging)은 데이터보다 로그를 먼저 디스크에 기록하는 규칙이다. 검사점(Checkpoint)은 주기적으로 변경을 디스크에 반영했다는 표시로, 회복할 때 마지막 검사점 이후만 보면 된다.

트랜잭션상황회복 작업
T1검사점 전에 커밋없음
T2검사점 뒤, 장애 전에 커밋REDO
T3장애 시점에 아직 실행 중UNDO

회복 기법에는 커밋 때까지 DB에 쓰지 않는 지연 갱신(REDO만), 바로 쓰는 즉시 갱신(UNDO·REDO, InnoDB 방식), 로그 없이 이전 페이지 테이블로 되돌리는 그림자 페이징이 있다.

  3. 2단계 잠금 규약(2PL)에 대한 설명으로 옳지 않은 것을 고르시오.
    • (A) 확장 단계에서는 잠금을 얻기만 한다.
    • (B) 모두 2PL을 지키면 직렬 가능성이 보장된다.
    • (C) 2PL을 지키면 교착상태가 발생하지 않는다.
정답과 해설

1. ROLLBACK TO SAVEPOINT s2;에서 ERROR 1305 (42000): SAVEPOINT s2 does not exist가 난다. s1으로 되돌아가면 그 뒤에 만든 s2도 사라지기 때문이다. 값은 6000(s1) → 4000(s2) → 4300 → s1로 복귀해 6000 → 오류 → 6500 → COMMIT이므로 6500이다.

2. 오손 읽기(Dirty Read). 취소된 값(4800)을 읽었다. 막는 가장 낮은 수준은 READ COMMITTED다.

3. (C). 2PL은 직렬 가능성을 보장하지만, 확장 단계에서 서로 상대의 잠금을 요청하면 교착상태가 생긴다.
